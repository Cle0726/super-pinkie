# C.le. 内核接管 · 计划书

- 计划：Windows 端 Opus 5.5，2026-11-20。执行：其他 AI，通过 `PROGRESS.md` 交接；K0 到 K5 的 Mac 部分由 Mac 端执行。验收：另一个 AI，按 `ACCEPTANCE.md` 进行。
- 配套文件：`ACCEPTANCE.md`、`PROGRESS.md`。和 `briefs/maintenance-1120/`（维护计划）一起读，两份计划的先后关系见第四节。
- 基线：碧琪主线 `2c1fa0bb28d6326d5459376748a8440f155d80ab`（v2.5.51）。OpenClaw 上游：`github.com/openclaw/openclaw`，MIT 许可证。文中的事实都在 11-20 核对过；动手前先 `git fetch`，有出入时以实际为准，并写进 `PROGRESS.md`。
- 内核新仓库建好之前，本计划放在碧琪仓库；新仓库建好以后，在新仓库的 `docs/` 里放一份副本，以碧琪仓库这份为准。

## 一、用户要什么

用户原话（11-20）：

- 「如果改 OpenClaw 的源码可以让碧琪更加好吗，其实我想做自己的 harness」
- 「我自己做这个项目很久了，不想老是挂别人的产品（尽量拿现在的 OpenClaw 所有结构来避免全部推翻重新做，后期我们可以自己维护自己的 harness）」
- 「要不要新开一个仓库？因为现在这个项目还有用户在使用」
- 内核的名字：「那叫 C.le.」
- 「我最怕的就是换了以后 UI 不适配，非常要紧，只是想后期能不能兼容 harness deepseek 的插件」

拆成要做到的事：

| 编号 | 要做到 | 怎么算做到 |
|---|---|---|
| H1 | 内核是自己的：源码在自己的仓库里，自己编译，不再从 npm 装别人的成品 | 碧琪发出去的 Mac 和 Windows 包里，内核都来自 `cle-core` 仓库的固定版本 |
| H2 | 不推倒重来：沿用 OpenClaw 现有的全部结构 | `cle-core` 的第一个提交就是上游源码原样；之后的改动都是一个一个的小提交 |
| H3 | **界面不能变**（用户最在意的一条） | 每一步切换前后，关键画面截图逐像素一致（沿用维护计划 M5 的截图基线）；界面相关的测试全部通过 |
| H4 | 现有用户不受影响 | 正式切换前，用户的 App 不会收到任何内核改动；切换时聊天记录、设置、记忆、模型配置都在，并且可以退回旧版 |
| H5 | 不再在成品上打补丁 | 碧琪 `patch/` 里改上游的补丁全部变成 `cle-core` 里正常的源码改动，并配有测试；Windows 不再需要 Mac 打好补丁的快照 |
| H6 | 对用户显示的内核名字是 C.le. | 关于页、启动信息、设置里能看到的内核名字是「C.le.」，并注明「基于 OpenClaw（MIT）」 |
| H7 | 以后能用 DeepSeek Harness 社区的插件 | 第一步：社区里的技能（SKILL.md）和 MCP 工具服务能装能用；第二步：经过可行性评估后，工具类的 dsh 插件能通过兼容层使用 |

**不做的事**（执行者不能自行增加）：

- 不换底座，不把 DeepSeek Harness 当底座（用户 11-20 选定：底座是 OpenClaw，DeepSeek Harness 只做插件兼容）。
- 不改界面外观；不搬用 DeepSeek Harness 的界面插件；本计划里所有改动都要求截图一致。
- 不改内部的技术名字：`openclaw` 包内部名、`~/.openclaw` 数据目录、配置文件名、环境变量名一律不动。改了会让用户的数据找不到，也会让以后合入上游的修复变难。只有用户看得到的显示名字改成 C.le.。
- 不跟着上游自动升级。上游的新版本只按第七节「上游规矩」挑选需要的修复。
- 不发版、不打 tag、不切换正式更新通道，除非用户点头（见第六节）。
- 不碰本机已安装的 App 和正式数据目录。

## 二、现状（代码事实，11-20）

1. **两个平台装内核的方式不一样**：
   - Windows：`desktop/windows/runtime-manifest.json` 固定写着 `"openclaw": "2026.7.1-2"`，`build-win.ps1:72` 从 npm 安装这个版本，再把 Mac 上打好补丁的 19 个文件（`desktop/windows/mac-runtime/`）盖上去。
   - Mac：`desktop/macos/build.sh:167` 读取**构建机上装着的** OpenClaw 版本（`:85` 一带还有一段兼容暂存）。仓库里没有固定版本号。
   - `patch/PORT-REPORT-2026.10.md` 把补丁迁移到了 `2026.10.4`，但正式发出去的版本用的是哪一版，要在 K0 里从发布包实测。
2. 上游仓库 `openclaw/openclaw` 是 MIT 许可证，主要语言是 TypeScript，另外还有 Swift、Kotlin、Rust 等（手机端和原生 App）。**完整历史约 16GB**；上游的 tag `v2026.7.1-2`、`v2026.10.4` 都存在。npm 包里只有编译好的 `dist/`，没有源码（`src/` 下只有一个说明文件）。
3. 磁盘：11-20 时 F 盘只剩 13GB，C 盘 38GB。**不能完整克隆上游历史**。
4. 碧琪对 OpenClaw 的依赖面：
   - 补丁：35 个 `patch/apply-*.mjs`，顺序手写在 `installer/macos/apply-theme.sh:486-552` 和 `install.sh:29-60` 两处。
   - 插件接口：`services/mode-architecture/index.mjs` 里有 23 个 `api.on`、15 个 `registerGatewayMethod`，以及其他服务（`services/*/package.json` 里的 `"openclaw"` 字段声明插件入口）。
   - 界面：`ui/injections/` 叠加在 OpenClaw 控制台页面上（121 个脚本、76 个样式表），`ui/runtime/` 里有上游编译出来的页面分块，碧琪改过它的缓存键。
   - 数据：用户数据在 `~/.openclaw/`（Windows 上在对应的用户目录下）。
5. 用户看到的内核名字目前是「CLE Kk」（例如 `app/super_pinkie.py`、`app/windows_desktop.py`、`desktop/macos/pinkie/Sources/Launcher.swift`、`CHANGELOG.md` 里都有）。
6. DeepSeek Harness（`deepseek-ai/deepseek-harness`，简称 dsh）：MIT 许可证，TypeScript，建立在插件框架 Cordis 之上，自称「一切都是插件」，11-20 时最新版本是 `dsh-v0.2.2-rc.5`，官方写明处于开发者预览阶段，**会有不兼容的改动**。工具通过 `ctx.tools` 注册。
7. 带 `dsh-plugin` 标签的 GitHub 仓库有 3 万多个，但按星数排在前面的，很多其实是**通用技能**（SKILL.md，例如 `tt-a1i/archify`、`alchaincyf/nuwa-skill`）、**MCP 工具服务**，或者是为了曝光打了标签的独立软件。真正只能在 dsh 里跑的 Cordis 插件，主要是模型接入、桌面壳、插件市场这类。
8. 碧琪现在已经有的兼容基础：
   - 技能：`skills/` 下有 167 个 SKILL.md 格式的技能，其中就包括 `archify`。
   - MCP：OpenClaw 自带 MCP 运行时（dist 里有 `agent-bundle-mcp-*`），碧琪在 `services/mode-architecture/rich-runtime.mjs:303-457` 有连接器目录，通过 `openclaw mcp` 管理 `mcp.servers`。

## 三、总体做法

1. **先证明「自己编译的 = 现在用的」，再改任何东西。** K2 用原样的上游源码自己编译一个内核，换进碧琪，所有测试和截图都必须和现在一样。这一步过了，后面每一个改动出问题，就只可能是改动本身造成的。
2. **界面是红线。** 本计划每一批都以维护计划 M5 的截图基线作为必过项。M5 没做完之前，K2 及以后的批次都不能开始。
3. **一个补丁一个提交。** 补丁搬进源码时，每次只搬一个，配一个测试，碧琪这边同步删掉对应的补丁文件，测试必须全部通过。
4. **两个仓库，各管各的。** `cle-core` 只管内核，按版本号发布编译好的包；碧琪仓库在清单文件里写明用哪个版本。碧琪发版之前，用户拿不到任何内核改动。

## 四、和维护计划的关系

- 维护计划 `briefs/maintenance-1120/` 按调整后的顺序进行：M0 → M1 → M2 → M5 → (M3 收窄 ∥ M4) → M7。**M6 取消**，由本计划的 K3 取代。M3 只保留区域负责表、共用观察器和全局变量棘轮，取消大规模的 CSS 分层改造（这一项本身就有改动界面的风险，而用户最在意的就是界面）。
- 本计划的 K0、K1 只做测量和建仓库，不改碧琪，可以和维护计划同时进行。
- **K2 必须等维护计划的 M0 和 M5 合进主线以后才能开始**（需要棘轮测试和截图基线）。
- K6（界面搬进源码）在 M3 收窄版完成以后才能开始。

## 五、分批

### K0 · 摸底（只测量，不改任何东西）

1. 从 v2.5.51 的发布包实测内核版本：解压 `super-pinkie-macos-2.5.51.zip` 和 `super-pinkie-windows-2.5.51-portable.zip`，读取里面 `openclaw/package.json` 的 `version`，并对比两边 `dist/` 的文件清单和哈希。
2. 定下接管的基准版本：两个平台一致，就用这个版本；不一致，就用 Mac 包的版本（Windows 盖上去的补丁文件来自 Mac），并在 `PROGRESS.md` 里写明 Windows 换版本带来的额外风险。**接管过程中不升级上游版本。**
3. 只拉基准版本的源码：`git clone --depth 1 --branch v<版本> https://github.com/openclaw/openclaw.git`，放在空间够的盘上（先查剩余空间；F 盘不够就放 C 盘），记录源码占用的大小。
4. 在 Windows 上按上游的说明编译（读上游的 `package.json`、`pnpm-workspace.yaml` 和开发文档），记录：Node 和 pnpm 的版本、耗时、产物位置，以及产物和 npm 包 `openclaw@<版本>` 的文件清单有哪些差异。Mac 端同样做一遍。
5. 列一张「碧琪用到了 OpenClaw 的哪些部分」的表：网关、控制台界面、对话运行时、模型传输、MCP、技能、会话、电脑操控扩展（`extensions/cua-computer`）等等，以及完全没用到的部分（手机 App、原生 App、各种聊天渠道等）。这张表供 K1 决定新仓库带哪些目录，也供以后瘦身用。
6. 把 35 个补丁逐个对应到源码里的位置（用补丁的锚点文字，在源码里找到对应的函数和文件），写成 `briefs/cle-core-1120/PATCH-MAP.md`：补丁名、改的是什么、源码文件和函数、搬进源码的难度（易 / 中 / 难）。

### K1 · 建内核仓库

1. 新建**私有**仓库 `Cle0726/cle-core`（建之前要用户点头，见第六节）。
2. 第一个提交 = 基准版本的上游源码原样，提交说明里写明上游的 tag 和提交号。如果 K0-5 显示有大块目录（例如手机 App）碧琪完全用不到，**第二个提交**再删掉它们，必须确认编译和测试不受影响。第一个提交始终保持原样，方便以后对照上游。
3. 保留上游的 `LICENSE`，原版权声明一个字都不改；新增 `NOTICE`：「C.le. 内核基于 OpenClaw（MIT 许可证，Copyright (c) 2026 OpenClaw Foundation）」。新增 `UPSTREAM.md`：记录基准版本、上游地址，以及以后挑选上游修复的记录表。
4. CI：在 Linux、Windows、macOS 上编译，并运行上游自带的测试（先记录基准版本自带测试本身的通过情况，作为对照），产出编译好的包（和 npm 包结构相同的 tarball），按 `cle-core-v<基准版本>-c.<序号>` 发布到这个仓库的 Releases。
5. 根目录写 `CLAUDE.md` 和 `AGENTS.md`：这个仓库是什么、怎么编译、怎么测试、不改内部技术名字、一个改动一个提交并配测试、补丁对照表在哪里。

### K2 · 换成自己编译的内核（原样，不改任何东西）

1. 碧琪新增内核清单 `core-manifest.json`：内核版本、下载地址、sha256。`build-win.ps1`、`desktop/macos/build.sh` 和安装脚本都改为从这个清单安装 `cle-core` 的编译包，不再从 npm 安装 `openclaw@<版本>`，也不再读取构建机上装着的 OpenClaw。
2. 现有的补丁流程**照常**在这个内核上运行，Windows 照常使用 Mac 快照。这一批只证明「自己编译的内核」和原来的完全等价。
3. 证明等价：碧琪全量门禁通过；截图基线全部一致；`tools/metre/inject-inventory.mjs` 的注入逐字一致；补丁的执行结果和原来一样（每个补丁都是 `applied` 或 `already`）；Windows 冒烟测试通过；Mac 端在隔离环境里跑一遍。
4. 这一批**不发版**。合进碧琪主线以后，下一次正式发版才会带上，届时按 K5 的发布规矩进行。

### K3 · 补丁搬进源码

1. 按 `PATCH-MAP.md` 从易到难，一次搬一个补丁：在 `cle-core` 里改源码，加一个测试，证明这个行为成立（优先复用碧琪 `tests/` 里对应的测试思路）；发一个新的内核小版本；碧琪更新 `core-manifest.json`，从补丁顺序里去掉这个补丁，删除补丁文件。每搬一个，碧琪全量门禁和截图基线都要通过。
2. 改控制台界面资源的补丁（例如 `apply-chat-linebreaks`、`apply-chat-timeline`、`apply-composer-drafts`、`apply-control-ui-file-delivery`）在 `cle-core` 的界面源码里改，碧琪 `ui/runtime/` 里的上游页面分块改为从内核包里取，碧琪仓库不再存放这些分块。
3. `apply-chat-math` 在 PORT-REPORT 里标记为「需人工」：如果基准版本上它本来就能打上，就照常搬进源码；如果打不上，就照现状处理（不生效），并在 `PATCH-MAP.md` 里标明，不在本计划里补做。
4. 全部搬完后：碧琪 `patch/` 下只剩和上游无关的工具（如果有）；`desktop/windows/mac-runtime/` 删除，Windows 直接使用 `cle-core` 的编译包；`refresh_mac_runtime.py` 退休。

### K4 · 显示名字改为 C.le.

1. 用户看得到的「CLE Kk」全部改为「C.le.」：关于页、启动画面、设置、托盘或菜单、错误提示、更新说明模板。先用 `grep -rn "CLE Kk"` 列出全部位置，逐条判断是否用户可见，写进 `PROGRESS.md`。
2. 关于页加一行：「C.le. 内核 <版本> · 基于 OpenClaw（MIT）」。
3. 文件夹名、包名、仓库名这些技术名字一律用 `cle-core`、`cle`，不带点（Windows 会去掉文件夹名末尾的点）。
4. 只改文字，不改布局；截图基线里包含这些文字的画面，按用户确认过的新文字更新基线，并且**只允许这些文字所在区域有差异**（贴出差异图）。

### K5 · 正式切换（发版）

1. 发版前，在隔离环境里从 v2.5.51 升级到新版本：聊天记录、设置、记忆、模型配置、技能、连接器全部保留；再从新版本退回 v2.5.51，同样全部保留。Mac 和 Windows 都要测。
2. 先发一个测试版，只给用户自己（或用户指定的少数人）安装，使用至少 3 天，没有新问题再正式发版。如果更新系统不支持测试通道（K0 时查清楚 `tools/release/release_assets.py` 里的 `channel`），就用手动安装的测试包代替，不能借正式通道试验。
3. 正式发版要用户点头。

### K6 · 界面搬进源码（长期，一块一块来）

1. 前提：M3 收窄版完成，区域负责表已经有了。
2. 从 `HOTSPOTS.md` 里最常出问题的区域开始，把这块区域的注入脚本和样式改写进 `cle-core` 的控制台界面源码，成为页面本来就有的部分，然后删掉对应的注入文件。
3. **每一块都必须截图逐像素一致**，界面测试全部通过。一块一个 PR，内核和碧琪两边一起合。
4. 这一批没有结束时间，做一块算一块。每做完一块，棘轮测试的基线同步变小。

### K7 · DeepSeek Harness 插件兼容

分三步走，前一步验收通过，才做下一步。

1. **社区技能**：在碧琪里支持「从 GitHub 仓库地址安装技能」。仓库里有 SKILL.md 的，按碧琪现有的技能格式安装（字段不同就做转换，写明转换规则）。安装前展示技能里包含的全部文件，脚本文件要高亮提示，用户确认后才装；不自动更新。用 5 个带 `dsh-plugin` 标签的真实技能仓库验收。
2. **MCP 工具服务**：在现有连接器目录（`rich-runtime.mjs` 的 `CONNECTOR_CATALOG` 和 `pinkie.connectors.*`）里支持添加自定义 MCP 服务，并能识别 dsh 插件仓库里附带的 MCP 服务配置。用 3 个真实的 MCP 类插件验收。
3. **Cordis 插件兼容层（先做评估，再决定做不做）**：
   - 评估：挑出 10 个最受欢迎、**真正需要 dsh 才能跑**的插件（排除技能、MCP 和独立软件），逐个读源码，列出它们用到的 `ctx.*` 服务。写成 `briefs/cle-core-1120/DSH-COMPAT.md`。
   - 判断标准：如果其中至少 6 个只用到工具注册（`ctx.tools`）、凭据、文件、网络这几类服务，就在 `cle-core` 里做一个兼容层 `packages/dsh-compat`：内嵌 Cordis，提供这几类服务的替身，把插件注册的工具接到 OpenClaw 的工具系统上。达不到这个标准，就写明原因，用户决定后再说。
   - 兼容层**只支持工具类插件**。替换对话主循环、会话记录、模型接入的插件，以及任何界面插件，一律不支持，因为它们会和碧琪自己的界面、模式冲突。
   - 固定兼容层对接的 dsh 版本；dsh 出了不兼容的新版本，不跟进，除非另立计划。
4. **安全规矩（三步都适用）**：社区的东西一律不自动安装、不自动更新；安装前给用户看来源和内容；需要执行命令、读写用户文件或联网的，要明确提示；无限制模式和 Metre 默认不加载社区插件，用户单独打开才加载。宣称「免费、不限量使用各家模型」这类来路不明的模型接入插件，不进入任何推荐清单。

## 七、上游规矩（K1 以后一直有效）

1. 每月查看一次上游的 Releases 和安全公告，凡是和碧琪用到的部分有关的修复，记进 `UPSTREAM.md` 的表格：上游提交、内容、要不要挑、理由。
2. 安全修复必须挑；功能更新默认不挑，用户想要某个新功能时另立计划。
3. 挑选用 `git cherry-pick` 或照着改，每一条配一个测试，按正常的小版本发布，碧琪那边全量门禁和截图基线都要通过。

## 八、风险

| 风险 | 后果 | 怎么防 |
|---|---|---|
| 自己编译的内核和 npm 成品有细微差异 | 碧琪行为变化 | K2 只换内核不改任何东西，用全量门禁、截图和注入对比三重证明等价 |
| 上游源码在 Windows 上编译不了 | Windows 无法从源码编译 | K0 就在 Windows 上试编译；编译不了时 CI 在 Linux 上编译跨平台的部分，原生部分写明来源，不能让 Windows 退回到使用 Mac 快照 |
| 磁盘空间不够 | 克隆或编译失败 | 只做浅克隆；K0 记录大小；完成后清理中间产物 |
| 搬补丁时改错 | 行为变化 | 一个补丁一个提交，配测试；碧琪全量门禁和截图每次都要过 |
| 用户升级以后数据找不到 | 聊天记录、设置丢失 | 不改内部技术名字和数据目录；K5 做升级和回退的实测 |
| 社区插件有恶意代码 | 用户电脑被破坏、数据泄露 | K7 的安全规矩；兼容层只开放工具类插件；高权限模式默认不加载 |
| dsh 还在预览期，接口常变 | 兼容层失效 | 固定对接版本，不自动跟进 |

## 九、接手规矩（执行者必读）

0. **先读 `briefs/program-1120/CONCURRENCY.md`**：多个 AI 同时干活的规矩，以及随时可能中断时怎么写接力卡。它和下面各条冲突时，以它为准。
1. 开工前先 `git fetch`；碧琪仓库从最新的 `origin/main` 切短分支；`cle-core` 同样一项任务一条短分支。
2. 每做完一步，在 `PROGRESS.md` 补一行，写明做了什么、怎么验证的、`ACCEPTANCE.md` 对应条目的自查结果（过 / 没过 / 没测和原因）。
3. 计划没写到的细节自己决定，写进 `PROGRESS.md` 的「执行者的决定」；只有第六节列出的事情需要问用户。
4. 不碰本机已安装的 App 和正式数据目录；所有运行都在隔离环境里（临时数据目录、假网关或隔离网关）。
5. 结束时清理自己产生的临时文件和中间产物（`PROGRESS.md` 引用的证据除外），C 盘和 F 盘空间都很紧张。
