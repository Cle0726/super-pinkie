# 碧琪代码维护 · 验收标准

对应 `PLAN.md`。验收方式（用户 2026-11-20 决定）：**每一批由执行者对照本文件自查**，逐条填写「过 / 没过 / 没测（原因）」，写进自己这一批的记录（M0 写在 `PROGRESS.md`，M1 起写在 `progress/<批号>.md`）；**全部做完以后统一验收**，由别的 AI 按本文件逐条亲自核对，结果写进 `review/<批号>.md`。流程和报告格式见 `briefs/program-1120/ACCEPTANCE.md`。

## 统一验收时验收人的规矩

1. **只认证据**：命令输出、测试结果、截图和差异图、`git` 记录、现场文件。`PROGRESS.md` 里写的「过」只当线索，不能当结论。
2. **必须亲自重跑的**：Z1 全量门禁、Z3 截图比对、Z4 棘轮测试，以及每批里带 ★ 的条目。
3. **判定**：带 ★ 的是必过项，任何一条没过，这一批就不过。不带 ★ 的，每批最多允许一条没过，而且要写明理由，说明为什么不影响用户。「没测」不算过。
4. **`REVIEW.md` 怎么写**：每一条写结论、证据（文件路径、命令、输出原文片段）和复现命令。发现的问题另列一张表：严重程度（阻塞 / 重要 / 次要）、位置、复现步骤、建议。
5. 验收人只核对，不改代码。发现问题交回执行者。

## 基线

- 回归对照固定为主线 `2c1fa0bb28d6326d5459376748a8440f155d80ab`，不跟着 `origin/main` 滚动。如果中途主线因为别的任务前进了，按 Metre 角色计划的先例处理：新的对照提交由验收人指定，从**独立的干净工作树**重新采集，旧结果原样保留，差异照列。
- M5 的截图基线在 M5 里采集，从此作为 M3、M4 及以后各批的外观对照。
- **M1 的例外**：M1 合进来的 B 类分支（例如学习台游戏 v4）本身就是功能改动，所以 M1 不适用 Z5 的逐字对比。M1 改为证明两件事：合并前后 Z1 都通过；合并带进来的差异只来自那条分支（`git diff <合并前主线> <合并后主线>` 和 `git diff <合并前主线>...<分支>` 一致）。这些分支带来的计数增加，在合并 PR 里写进 `tools/health/exceptions.json`，原因写「来自合并 <分支名>」。M1 全部合完以后，Z5 的对照改为 M1 结束时的主线提交，写进 `PROGRESS.md`。

## M2 · 版本号自动生成

- **M2-1 ★** 仓库源码里没有手写版本号：`measure.mjs` 统计到的手写版本号为 0（`?v=` 后面只会是 `@hash`），`ui/runtime/index-*.js` 的缓存键不再需要手动刷新。
