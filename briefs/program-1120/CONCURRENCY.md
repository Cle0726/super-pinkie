# 多个 AI 同时干活的规矩

适用于这次整体计划的每一个执行者和验收人，不管是 Codex、Claude 还是别的 AI，也不管在 Windows 还是 Mac 上。**开工前必读**，和自己那一批的 `PLAN.md`、`ACCEPTANCE.md` 一起读。

用户只会把 `START.md` 发给 AI，不会指定做哪一批。AI 按**第九节「自己挑活」**自己看清现状、挑一件没人在做的事去做。多个 AI 拿到的是同一个文件，也会各自挑到不同的事，同时推进。

这些规矩针对的是这个项目真实出过的问题：远端历史被改写过，本机有几十个旧工作区，修复散在很多分支上，合并时被冲掉。

---

## 〇、随时可能断：边做边写接力卡（最重要的一条）

任何一个 AI 都可能做到一半就停：额度用完、对话太长、被用户打断、电脑重启。下一个接手的 AI 可能是别的模型，也可能在另一台机器上，它**只能看到推送到 GitHub 上的东西**。所以：

1. **每做完一小步就提交并推送**，最长 30 分钟必须推送一次。没做完的也推送，提交说明写 `maint(M2) wip: <做到哪>`。只存在本机、没推送的改动，对下一个 AI 来说等于不存在。
2. **接力卡**：每一批的记录文件 `briefs/<计划>/progress/<批号>.md` 最上面固定放一张接力卡（M0 的记录在 `PROGRESS.md` 里，同样适用）。下面几种时候**必须**更新接力卡，并和代码一起推送：
   - 每完成一个步骤；
   - 开始任何超过 5 分钟的操作之前（全量测试、编译、克隆、打包），写明正在跑什么、预计多久、结果会写到哪个文件；
   - 做了一个计划里没写的决定；
   - 试了一个办法但不行（写明试了什么、为什么不行，免得下一个 AI 再试一遍）。

   接力卡的格式，照抄后填写：

   ```markdown
   ## 接力卡（最后更新：2026-11-21 14:30，Codex @ Windows）

   - 状态：进行中 / 卡住：<原因> / 自查通过 / 已合并 / 返工
   - 分支和 PR：`maint/m2-asset-hash`，PR #41（草稿）
   - 已完成：
     1. <步骤>（提交 `abc1234`）
     2. <步骤>（提交 `def5678`）
   - 正在做：<第几步，做到哪一半>
   - 下一步：<具体到下一个 AI 照着就能做，例如「运行 X，把输出和 Y 对比，不一致就改 Z」>
   - 没推送的东西：无 / <在哪个文件夹，是什么，为什么还没推>
   - 环境：工作区 `F:\Projects\pinkie-wt\m2-exec`；临时目录 `F:\tmp\pinkie-m2-exec-7c1a`；端口 5120–5122；后台进程 <名称和进程号，怎么停>
   - 正在跑的长操作：无 / <命令，开始时间，结果文件>
   - 踩过的坑：<试过不行的办法和原因>
   - 待用户决定：无 / <事情>
   ```

3. **接手的 AI 先做这几件事，再动手**：
   1. `git fetch origin`，读这一批的接力卡和 PR 里的最新留言；
   2. 如果在同一台机器、原来的工作区还在：先在那个文件夹里看 `git status`，有没推送的改动，判断要不要保留（保留就提交推送，并在接力卡上写明「接手时发现并保留」）；换了机器的，就从远端分支建自己的工作区；
   3. 按接力卡「环境」一栏，确认上一个 AI 留下的后台进程和端口已经停掉（停之前确认确实是它留下的）；
   4. 用最快的办法核实「已完成」的最后一步确实成立，例如重跑那一步的检查命令；
   5. 在接力卡上改「最后更新」为自己，在 PR 里留言「接手：<AI 名称>，<机器>，<日期>，从『下一步』继续」，然后照「下一步」往下做。
4. **统一验收的验收人同样写接力卡**，写在 `review/<批号>.md` 的最上面：已经核对了哪些条目、核对的是哪个提交、下一条要核对什么。
5. **每次推送前先看一眼 PR 留言**（`gh pr view <号> --comments`）。如果在你上一次推送之后，有别的 AI 留言「接手」，说明它以为你已经停了：不要再推送，在 PR 里回复说明你还在，然后告诉用户，由用户决定谁继续。

## 一、一个批次 = 一个 AI = 一条分支 = 一个文件夹

1. **一个文件夹同一时间只给一个 AI 用。** 两个 AI 在同一个文件夹里切换分支，会互相覆盖对方没提交的改动。
2. 碧琪主文件夹 `F:\Projects\super-pinkie` 在 PROGRESS 表里写明归谁用（目前是 M0 的执行者）。其他人一律用自己的工作区：
   ```
   git -C F:\Projects\super-pinkie fetch origin
   git -C F:\Projects\super-pinkie worktree add F:\Projects\pinkie-wt\<批号>-<角色> -b <分支名> origin/main
   ```
   `<角色>` 写 `exec`（执行）或 `review`（验收），例如 `F:\Projects\pinkie-wt\m2-exec`。验收人用分离头（`--detach`），不建分支。
3. 碧琪的一份完整工作区约 0.4GB（不含 `node_modules`）。开工前先看磁盘剩余空间：F 盘低于 5GB 时改放 C 盘，例如 `C:\pinkie-wt\…`。
4. **不要动别人的工作区。** 这台机器上已经有二十多个旧工作区（`git worktree list` 可以看到，多数是 11-19 之前 Metre 相关的）。清理旧工作区属于 M1，由 M1 的执行者先确认没有未提交的改动、对应分支已经合并或已存档，再统一清理。
5. 批次合并以后，执行者用 `git worktree remove` 删掉自己的工作区，并删除本机的同名分支。

## 二、开工前：认领

1. **先看有没有人在做。** 查看两份 `PROGRESS.md` 的表格，以及 GitHub 上还开着的 PR（`gh pr list --state open`）。
2. **用草稿 PR 认领。** 从最新的 `origin/main` 切出分支，推送一个空提交或第一个提交，马上开一个**草稿 PR**：
   - 标题：`maint(M2): <一句话>` 或 `core(K0): <一句话>`；
   - 正文第一段写「认领：<AI 名称>，<机器>，<日期>」，下面列出**这一批要改的文件**（以 `README.md` 第一节的独占文件为基础，加上你实际要改的）。
3. **检查独占文件有没有冲突。** 你要改的文件，如果出现在别的已开 PR 的文件清单里，就不能开工：换一批做，或者等对方合并。两边都只是新增不同的文件，不算冲突。
4. **前置条件没满足不开工。** `README.md` 第一节写的「前置条件」必须是已经合进 main 的状态，不能是「快做完了」。
5. 一批看起来「断了」（判断标准见 9.4），别人可以在那个 PR 下留言「接手」，然后基于它的分支继续做；原来的认领者回来时先看留言（〇.5）。

## 三、干活时

1. **分支名和提交说明带批号**：分支 `maint/m2-…`、`core/k0-…`；提交说明以 `maint(M2):`、`core(K0):` 开头。这样看历史就知道是哪一批改的。
2. **只改自己认领的文件。** 做的过程中发现必须改别的文件，先更新 PR 正文里的文件清单，并重新检查有没有冲突（2.3）。
3. **每天至少变基一次**：`git fetch origin && git rebase origin/main`。变基后重跑和自己这一批相关的测试。
4. **隔离环境的端口和临时目录不能撞车。** 正式网关在 18789 端口，任何人都不许碰。测试用的假网关、试玩服务、浏览器调试端口，一律按下表取用（执行者用基数，验收人用基数加 5）：

   | 批 | 端口基数 | 批 | 端口基数 |
   |---|---|---|---|
   | M0 | 5100 | K0 | 5200 |
   | M1 | 5110 | K1 | 5210 |
   | M2 | 5120 | K2 | 5220 |
   | M3 | 5130 | K3 | 5230 |
   | M4 | 5140 | K4 | 5240 |
   | M5 | 5150 | K5 | 5250 |
   | M7 | 5170 | K6 | 5260 |
   |  |  | K7 | 5270 |

   某个工具不支持指定端口时，用它之前先确认那个端口没人占用（`Get-NetTCPConnection -LocalPort <端口>`）；被占用就等，或者和占用者错开时间。
   临时目录一律叫 `<盘>:\tmp\pinkie-<批号>-<角色>-<随机串>`（例如 `F:\tmp\pinkie-m2-exec-7c1a`），不要和别人共用 HOME、APPDATA、TEMP。
5. **生成出来的文件不手工合并。** 下面这些文件由工具生成，变基时遇到冲突，先取 main 的版本，再用工具重新生成：
   - `tools/health/baseline.json`：取 main 的版本，然后运行 `node tools/health/measure.mjs --write-baseline`，只会把你这一批真正改善的数字写进去（它拒绝写入增长）；
   - `tools/release-gate/known-failures.json`：取 main 的版本，**不许新增条目**；
   - `tests/visual/baseline/**`（M5 以后）：取 main 的版本，**不许为了通过测试而更新截图**，只有用户点过头的外观变化（目前只有 K4 的文字）才能更新；
   - 内核清单 `core-manifest.json`（K2 以后）：取 main 的版本，再写入你这一批要用的内核版本。
6. **记录分开写，避免互相冲突。**
   - 每一批的详细记录写在 `briefs/<计划>/progress/<批号>.md`（M0 已经写在 `PROGRESS.md` 里，保持原样不动；M1 起按这条来）。
   - `PROGRESS.md` 顶部的总表，只改自己那一行，而且只在自己这一批的 PR 里改。变基时这张表冲突了，两边的行都保留。
   - 验收报告写在 `briefs/<计划>/review/<批号>.md`。
7. **全量测试别同时跑太多。** 在隔离环境里，Windows 上跑一遍全量门禁约 3 分钟（M0 实测 158 秒）。同一台机器上最多同时跑两路；跑出来的失败，先单独重跑那个文件再下结论。
8. **开工先确认护栏还拦得住。** 因为平时不单独验收，护栏一旦失灵，后面每一批的自查都是空的。所以 M0 合并以后，每一批开工时，先在本地做一个小反例：随便在一个已有的 CSS 文件里加一处 `!important`，确认棘轮测试失败；M5 合并以后，再把一个按钮挪动几个像素，确认截图测试失败。做完马上还原，绝不提交，结果记进接力卡。护栏拦不住时，按第七节停下来。

## 四、合并时

1. **一次只合一个。** 准备合并的人先看有没有别的 PR 正在合并，或者刚合进来还没跑完 CI。有的话等它的 CI 跑完。
2. **合并前的最后检查**：变基到最新的 main，重跑这一批的必过项和棘轮测试，确认 CI 全绿。自查通过以后分支又有了新提交（返工或变基带来的），就把第五节的必做自查重新做一遍。
3. **自查通过就自己合并，不用问用户**（用户 2026-11-20 的决定：「他们做完不会自己合吗？难道每次都问你？」）。以下条件**全部**满足，AI 自己合并：
   - 接力卡是「自查通过」，带 ★ 的条目**全部是「过」**。有「没测（需 Mac / Windows）」的，等另一台机器的 AI 补测完再合；
   - 已经变基到最新的 main，PR 上的 CI 全部是绿的（K2 以后包括「C.le. 内核」那一路）；
   - 不在主线冻结期（4.4）；没有别的 PR 正在合并，或者刚合进来还没跑完 CI（4.1）；
   - 碧琪没有正在进行的正式发版：没有开着的 `release/*` PR，`release.yml` 和 `release-candidate.yml` 也没有正在跑的任务（`gh run list --workflow release.yml --status in_progress`）。

   合并前在 PR 里留言「自动合并：自查通过，CI 全绿，满足 CONCURRENCY 4.3」，然后用 `gh pr merge <号> --merge --delete-branch` 合并。**不许用 `--admin` 跳过检查，不许强推 main。** 合并前的最后一个提交里，把接力卡和 `PROGRESS.md` 总表中自己那一行改成「已合并」；来不及的话，合并后马上开一个小 PR 改。

   **合并后主线变红就回滚**：合并后盯着 main 上这次合并的 CI。如果是这次合并弄红的，30 分钟内修不好，就用 `git revert` 开一个回滚 PR，CI 绿了马上合并，让主线回到随时能给用户发版的状态；然后这一批改为「返工」。
4. **主线冻结**：M1 合并 B 类分支期间、统一验收期间、K5 发版期间，别的批次可以继续在自己的分支上干活，但不合并。统一验收期间唯一能合并的是返工 PR。冻结开始和结束都在 PROGRESS 表里写明。
5. **多人同时搬补丁（K3）**：可以各自在 `cle-core` 里开分支做不同的补丁，但 `cle-core` 的发版和碧琪这边 `core-manifest.json` 的更新**一次只做一个**，按搬完的先后排队。
6. 有人合并以后，**其他所有还开着的分支都要变基**，并重跑棘轮测试和与自己相关的测试，然后才能标「自查通过」或合并。

## 五、自查和统一验收

用户 2026-11-20 决定：**平时每一批只由执行者自查，全部做完以后统一验收。** 详细做法见 `ACCEPTANCE.md`。

1. **自查**：执行者按 `ACCEPTANCE.md` 第一节做必做自查，带 ★ 的条目逐条写证据。全部过了（或者只剩需要另一台机器补测的），接力卡状态改成「自查通过」，PR 改为可审阅，然后按 4.3 的条件自己合并（有「没测」条目的，等补测完再合）。
2. 自查通过以后，除了合并前的变基，**不再往这个分支推送新功能**。
3. **统一验收**：时间到了（见 `ACCEPTANCE.md` 开头的表），由没当过这些批次执行者的 AI 分组来做，每组用草稿 PR `program(review-1): <组名>` 认领。验收人**只读不改**：不改代码，不改测试，只提交自己组的 `review/<批号>.md` 和总检查文件，提交到自己组的分支上。
4. 统一验收发现问题的批次标为「返工」：在原来那一批的 PR 下留言，返工从最新的 main 切新分支来修，修完自查、合并，验收人再重核受影响的条目，带 ★ 的通用项（全量门禁、棘轮、截图对比、注入对比）一律重跑。
5. 写在 Mac 上才能核对的条目，Windows 上的 AI 一律记为「没测（需 Mac）」，不能记成「过」；反过来也一样。自查和统一验收都适用。

## 六、两台机器

1. Windows 和 Mac 用同一套认领方式（草稿 PR），同一个主线 `main`。不再使用 `audit/pinkie-1112`、`unify/pinkie-1112` 这种两边一起推的长期分支。
2. 只能在某一台机器上做的部分，在 PR 正文里写明「需 Mac」或「需 Windows」，由那台机器上的 AI 另外认领、补做，补做的结果写进同一个 `progress/<批号>.md`。
3. 开工前两边都先 `git fetch`。**基于 2026-11 改写前历史的旧本机分支一律不推送**：推送前看一下 `git rev-list --count origin/main..HEAD`，数字明显大于这一批的提交数（比如超过 50），就停下来。

## 七、遇到这些情况，停下来

停下来的意思是：不继续改，在 `progress/<批号>.md` 里写清楚情况，PR 状态写「卡住：<原因>」，等用户或协调者处理。

- 计划写的代码事实和实际不符，而且影响到怎么做（只影响数字的，写明差异后可以继续）；
- 带 ★ 的必过项自己检查没过，又不知道怎么修；
- 需要改别人认领的独占文件；
- 需要用户点头的事情（只有 9.7 列出的那几件）；
- 发现正式环境（本机已安装的 App、`~/.openclaw`、18789 端口）被改动过，不管是不是自己改的；
- 磁盘剩余空间低于 3GB。

## 八、收工

- 把接力卡的状态改成「自查通过」（或「已合并」），「下一步」写成合并前还要注意什么，然后推送；
- 删掉自己的临时目录和工作区（`progress` 里引用的证据除外）；
- 确认没有留下占着端口的进程；
- 在 `progress/<批号>.md` 末尾写一段大白话小结：做了什么、哪些过了、哪些没测和原因、下一批要注意什么。

## 九、自己挑活

用户只会把 `START.md` 发给 AI，不会指定做哪一批。每个 AI 按下面的步骤自己挑。多个 AI 同时这样做，会各自挑到不同的事。

### 9.1 先给自己起名字

格式：`<模型>-<机器>-<4 位随机字母数字>`，例如 `Codex-Win-7f3a`、`Claude-Mac-k29d`。认领、接力卡、PR 留言里都用这个名字。同一个模型开的两个会话，名字不同，算两个 AI。

### 9.2 看清现状

```
git fetch origin
gh pr list --repo Cle0726/super-pinkie --state open --json number,title,isDraft,headRefName,createdAt
```

- 标题以 `maint(`、`core(` 或 `program(` 开头的 PR，就是认领，括号里是批号（`program(review-1): <组名>` 表示第一次统一验收的某一组，`review-2` 是第二次）。草稿表示正在做；非草稿表示自查通过、等合并（可能在等补测、等冻结结束，或者 CI 还没绿）。
- 统一验收发现问题时，会在原来那一批的 PR 下留言「统一验收：返工，见 review/<批号>.md」。有这条留言、又还没有返工 PR 合并的批次，就处于返工状态。
- 每个认领 PR 都要看：最后一次推送的时间（`gh pr view <号> --json commits --jq '.commits[-1].committedDate'`）、留言（`gh pr view <号> --comments`）、分支上那一批的接力卡（`git show origin/<分支>:<记录文件路径>`）。
- 旧记录里写的「待验收」（例如 M0），按现在的规矩就是「自查通过」，满足 4.3 的条件就可以合并。
- 两份 `PROGRESS.md` 的总表，以 `origin/main` 上的为准（`git show origin/main:briefs/maintenance-1120/PROGRESS.md`，接管计划同理）。还没合并的批次，状态要看它分支上的接力卡。
- `README.md` 第一节：每一批的前置条件、独占文件、要在哪台机器上做。
- `cle-core` 仓库建好以后，它的 PR 也要看。

### 9.3 按顺序挑第一件能做的事

1. **合并**：有自查通过、满足 4.3 全部条件、却还没合并的 PR（执行者可能已经停了）。在 PR 下留言「合并认领：<名字>」，然后按 4.3 合并。
2. **接手**：有批次符合 9.4 说的「断了」。
3. **返工**：有批次处于返工状态，而且还没有人在修（或者修的人符合 9.4 的「断了」）。
4. **补测**：已经自查通过或已合并的批次里，有标着「没测（需 Mac）」或「没测（需 Windows）」的条目，正好是你这台机器能做的。
5. **统一验收**：到了统一验收的时候（`ACCEPTANCE.md` 开头的表：第一次是 M0–M5、M7 和 K0–K4 都已合并；第二次是 K5 已发布、K7 已合并），挑一个还没人认领的分组，而且组里的批次你都没当过执行者。`summary` 组要等其他组都写完才能挑。
6. **新开一批**：按 `README.md` 第一节表格的顺序，第一个同时满足以下条件的批次：
   - 前置条件**已经合进 origin/main**。K5 另外要求：第一次统一验收已经通过，并且记录里有用户同意切换的原话（K1 建仓库用户已经同意，不用再问）；
   - 没有任何开着的 PR 认领它，总表里也不是「已合并」；
   - 它的独占文件，没有出现在别的开着的 PR 的文件清单里；
   - 机器要求是「任一」，或者正好是你这台机器。
7. **都没有**：不要自己找计划外的事做。直接告诉用户：每一批现在是什么状态、各自卡在什么上（等合并、等用户点头、等前置批次、等统一验收）；**哪些 PR 自查通过却还没合并、为什么**（在等补测、等冻结结束、CI 没绿）；以及把所有接力卡里「待用户决定」的内容汇总成一张清单。

### 9.4 怎么判断一批「断了」

以下几条**同时**满足，才算断了：

- 接力卡状态是「进行中」或「返工」；
- 这条分支最后一次推送是 2 小时以前；
- 接力卡「正在跑的长操作」是空的，或者它写的预计结束时间已经过去 1 小时以上；
- PR 里最近 2 小时没有那个执行者的留言。

有一条不满足，就当它还在做，不要碰。状态是「卡住」的不算断了：卡住是在等用户或者计划本身有问题，只有接力卡上写明「卡住的原因已解决，可以继续」，才能接手。

### 9.5 两个 AI 挑中了同一件事

- **新开一批、统一验收的分组**：开完认领用的草稿 PR 以后，马上再列一遍开着的 PR。如果有别的 PR 也认领了同一批（或同一组），或者两边的独占文件重叠：**PR 编号小的留下**；编号大的那个关掉自己的 PR，留言「撞车，让给 #<号>」，删掉只有认领提交的远端分支，然后回到 9.3 重新挑。
- **合并、接手、返工、补测**：在那个 PR 下留言认领，例如「合并认领：Codex-Win-7f3a」「接手：Claude-Mac-k29d」「返工认领：…」「补测认领：…」。留言以后马上重新读一遍留言：同类认领里**最早的那条**留下；晚的那个补一条「让给 <名字>」，然后回到 9.3。

### 9.6 做完一件以后

在聊天里用大白话向用户简短汇报，然后回到 9.2 继续挑下一件，直到出现 9.3 第 7 条「都没有」，或者需要用户决定。中途随时可能因为额度停下，所以每一件事都要按第〇节写接力卡。
