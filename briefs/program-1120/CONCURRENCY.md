# 多个 AI 同时干活的规矩

适用于这次整体计划的每一个执行者和验收人，不管是 Codex、Claude 还是别的 AI，也不管在 Windows 还是 Mac 上。**开工前必读**，和自己那一批的 `PLAN.md`、`ACCEPTANCE.md` 一起读。

这些规矩针对的是这个项目真实出过的问题：远端历史被改写过，本机有几十个旧工作区，修复散在很多分支上，合并时被冲掉。

---

## 〇、随时可能断：边做边写接力卡（最重要的一条）

任何一个 AI 都可能做到一半就停：额度用完、对话太长、被用户打断、电脑重启。下一个接手的 AI 可能是别的模型，也可能在另一台机器上，它**只能看到推送到 GitHub 上的东西**。所以：

1. **每做完一小步就提交并推送**，最长 30 分钟必须推送一次。没做完的也推送，提交说明写 `maint(M2) wip: <做到哪>`。只存在本机、没推送的改动，对下一个 AI 来说等于不存在。
2. **接力卡**：每一批的记录文件 `briefs/<计划>/progress/<批号>.md` 最上面固定放一张接力卡（M0 的记录在 `PROGRESS.md` 里，同样适用）。下面几种时候**必须**更新接力卡，并和代码一起推送：
   - 每完成一个步骤；
   - 开始任何超过 5 分钟的操作之前（全量测试、编译、克隆、打包），写明正在跑什么、预计多久、结果会写到哪个文件；
   - 做了一个计划里没写的决定；
   - 试了一个办法但不行（写明试了什么、为什么不行，免得下一个 AI 再试一遍）。

   接力卡的格式，照抄后填写：

   ```markdown
   ## 接力卡（最后更新：2026-11-21 14:30，Codex @ Windows）

   - 状态：进行中 / 卡住：<原因> / 待验收 / 返工 / 已合并
   - 分支和 PR：`maint/m2-asset-hash`，PR #41（草稿）
   - 已完成：
     1. <步骤>（提交 `abc1234`）
     2. <步骤>（提交 `def5678`）
   - 正在做：<第几步，做到哪一半>
   - 下一步：<具体到下一个 AI 照着就能做，例如「运行 X，把输出和 Y 对比，不一致就改 Z」>
   - 没推送的东西：无 / <在哪个文件夹，是什么，为什么还没推>
   - 环境：工作区 `F:\Projects\pinkie-wt\m2-exec`；临时目录 `F:\tmp\pinkie-m2-exec-7c1a`；端口 5120–5122；后台进程 <名称和进程号，怎么停>
   - 正在跑的长操作：无 / <命令，开始时间，结果文件>
   - 踩过的坑：<试过不行的办法和原因>
   - 待用户决定：无 / <事情>
   ```

3. **接手的 AI 先做这几件事，再动手**：
   1. `git fetch origin`，读这一批的接力卡和 PR 里的最新留言；
   2. 如果在同一台机器、原来的工作区还在：先在那个文件夹里看 `git status`，有没推送的改动，判断要不要保留（保留就提交推送，并在接力卡上写明「接手时发现并保留」）；换了机器的，就从远端分支建自己的工作区；
   3. 按接力卡「环境」一栏，确认上一个 AI 留下的后台进程和端口已经停掉（停之前确认确实是它留下的）；
   4. 用最快的办法核实「已完成」的最后一步确实成立，例如重跑那一步的检查命令；
   5. 在接力卡上改「最后更新」为自己，在 PR 里留言「接手：<AI 名称>，<机器>，<日期>，从『下一步』继续」，然后照「下一步」往下做。
4. **验收人同样写接力卡**，写在 `review/<批号>.md` 的最上面：已经核对了哪些条目、核对的是哪个提交、下一条要核对什么。

## 一、一个批次 = 一个 AI = 一条分支 = 一个文件夹

1. **一个文件夹同一时间只给一个 AI 用。** 两个 AI 在同一个文件夹里切换分支，会互相覆盖对方没提交的改动。
2. 碧琪主文件夹 `F:\Projects\super-pinkie` 在 PROGRESS 表里写明归谁用（目前是 M0 的执行者）。其他人一律用自己的工作区：
   ```
   git -C F:\Projects\super-pinkie fetch origin
   git -C F:\Projects\super-pinkie worktree add F:\Projects\pinkie-wt\<批号>-<角色> -b <分支名> origin/main
   ```
   `<角色>` 写 `exec`（执行）或 `review`（验收），例如 `F:\Projects\pinkie-wt\m2-exec`。验收人用分离头（`--detach`），不建分支。
3. 碧琪的一份完整工作区约 0.4GB（不含 `node_modules`）。开工前先看磁盘剩余空间：F 盘低于 5GB 时改放 C 盘，例如 `C:\pinkie-wt\…`。
4. **不要动别人的工作区。** 这台机器上已经有二十多个旧工作区（`git worktree list` 可以看到，多数是 11-19 之前 Metre 相关的）。清理旧工作区属于 M1，由 M1 的执行者先确认没有未提交的改动、对应分支已经合并或已存档，再统一清理。
5. 批次合并以后，执行者用 `git worktree remove` 删掉自己的工作区，并删除本机的同名分支。

## 二、开工前：认领

1. **先看有没有人在做。** 查看两份 `PROGRESS.md` 的表格，以及 GitHub 上还开着的 PR（`gh pr list --state open`）。
2. **用草稿 PR 认领。** 从最新的 `origin/main` 切出分支，推送一个空提交或第一个提交，马上开一个**草稿 PR**：
   - 标题：`maint(M2): <一句话>` 或 `core(K0): <一句话>`；
   - 正文第一段写「认领：<AI 名称>，<机器>，<日期>」，下面列出**这一批要改的文件**（以 `README.md` 第一节的独占文件为基础，加上你实际要改的）。
3. **检查独占文件有没有冲突。** 你要改的文件，如果出现在别的已开 PR 的文件清单里，就不能开工：换一批做，或者等对方合并。两边都只是新增不同的文件，不算冲突。
4. **前置条件没满足不开工。** `README.md` 第一节写的「前置条件」必须是已经合进 main 的状态，不能是「快做完了」。
5. 认领超过 48 小时没有任何新提交，又没有在 PR 里说明原因，视为放弃。别人可以在那个 PR 下留言「接手」，然后基于它的分支继续做；原来的认领者回来时先看留言。

## 三、干活时

1. **分支名和提交说明带批号**：分支 `maint/m2-…`、`core/k0-…`；提交说明以 `maint(M2):`、`core(K0):` 开头。这样看历史就知道是哪一批改的。
2. **只改自己认领的文件。** 做的过程中发现必须改别的文件，先更新 PR 正文里的文件清单，并重新检查有没有冲突（2.3）。
3. **每天至少变基一次**：`git fetch origin && git rebase origin/main`。变基后重跑和自己这一批相关的测试。
4. **隔离环境的端口和临时目录不能撞车。** 正式网关在 18789 端口，任何人都不许碰。测试用的假网关、试玩服务、浏览器调试端口，一律按下表取用（执行者用基数，验收人用基数加 5）：

   | 批 | 端口基数 | 批 | 端口基数 |
   |---|---|---|---|
   | M0 | 5100 | K0 | 5200 |
   | M1 | 5110 | K1 | 5210 |
   | M2 | 5120 | K2 | 5220 |
   | M3 | 5130 | K3 | 5230 |
   | M4 | 5140 | K4 | 5240 |
   | M5 | 5150 | K5 | 5250 |
   | M7 | 5170 | K6 | 5260 |
   |  |  | K7 | 5270 |

   某个工具不支持指定端口时，用它之前先确认那个端口没人占用（`Get-NetTCPConnection -LocalPort <端口>`）；被占用就等，或者和占用者错开时间。
   临时目录一律叫 `<盘>:\tmp\pinkie-<批号>-<角色>-<随机串>`（例如 `F:\tmp\pinkie-m2-exec-7c1a`），不要和别人共用 HOME、APPDATA、TEMP。
5. **生成出来的文件不手工合并。** 下面这些文件由工具生成，变基时遇到冲突，先取 main 的版本，再用工具重新生成：
   - `tools/health/baseline.json`：取 main 的版本，然后运行 `node tools/health/measure.mjs --write-baseline`，只会把你这一批真正改善的数字写进去（它拒绝写入增长）；
   - `tools/release-gate/known-failures.json`：取 main 的版本，**不许新增条目**；
   - `tests/visual/baseline/**`（M5 以后）：取 main 的版本，**不许为了通过测试而更新截图**，只有用户点过头的外观变化（目前只有 K4 的文字）才能更新；
   - 内核清单 `core-manifest.json`（K2 以后）：取 main 的版本，再写入你这一批要用的内核版本。
6. **记录分开写，避免互相冲突。**
   - 每一批的详细记录写在 `briefs/<计划>/progress/<批号>.md`（M0 已经写在 `PROGRESS.md` 里，保持原样不动；M1 起按这条来）。
   - `PROGRESS.md` 顶部的总表，只改自己那一行，而且只在自己这一批的 PR 里改。变基时这张表冲突了，两边的行都保留。
   - 验收报告写在 `briefs/<计划>/review/<批号>.md`。
7. **全量测试别同时跑太多。** 在隔离环境里，Windows 上跑一遍全量门禁约 3 分钟（M0 实测 158 秒）。同一台机器上最多同时跑两路；跑出来的失败，先单独重跑那个文件再下结论。

## 四、合并时

1. **一次只合一个。** 准备合并的人先看有没有别的 PR 正在合并，或者刚合进来还没跑完 CI。有的话等它的 CI 跑完。
2. **合并前的最后检查**：变基到最新的 main，重跑这一批的必过项和棘轮测试，确认 CI 全绿；验收以后分支又有新提交的，按 5.4 处理。
3. **合并要用户点头**，在 PR 里贴出用户的原话。合并以后，执行者在自己 PR 的最后一个提交里（或者合并后马上开的一个小 PR 里）把 `PROGRESS.md` 总表中自己那一行改成「已合并」。
4. **主线冻结**：M1 合并 B 类分支期间，以及 K5 发版期间，别的批次可以继续在自己的分支上干活，但不合并。冻结开始和结束都在 PROGRESS 表里写明。
5. **多人同时搬补丁（K3）**：可以各自在 `cle-core` 里开分支做不同的补丁，但 `cle-core` 的发版和碧琪这边 `core-manifest.json` 的更新**一次只做一个**，按搬完的先后排队。
6. 有人合并以后，**其他所有还开着的分支都要变基**，并重跑棘轮测试和与自己相关的测试，然后才能请人验收或合并。

## 五、验收时

1. **执行者和验收人必须是不同的 AI 会话**，最好是不同的模型（例如 Codex 做的，交给 Claude 验；Claude 做的，交给 Codex 验）。验收人要从新的上下文开始，不接着执行者的对话。
2. 执行者把状态改成「待验收」以后，**就停止往这个分支推送**。验收人在自己的工作区里检出 PR 当时的最新提交，记下提交号。
3. 验收人**只读不改**：不改代码，不改测试。唯一可以提交的是 `review/<批号>.md` 这一个文件，提交到被验收的分支上。不通过的，把状态改成「返工」，交回执行者。
4. **验收以后分支又有新提交**（返工或变基）：验收人只重核受影响的条目，但带 ★ 的通用项（全量门禁、棘轮、截图对比、注入对比）一律重跑。报告里写明两次核对的提交号。
5. 写在 Mac 上才能核对的条目，Windows 上的 AI 一律记为「没测（需 Mac）」，不能记成「过」；反过来也一样。

## 六、两台机器

1. Windows 和 Mac 用同一套认领方式（草稿 PR），同一个主线 `main`。不再使用 `audit/pinkie-1112`、`unify/pinkie-1112` 这种两边一起推的长期分支。
2. 只能在某一台机器上做的部分，在 PR 正文里写明「需 Mac」或「需 Windows」，由那台机器上的 AI 另外认领、补做，补做的结果写进同一个 `progress/<批号>.md`。
3. 开工前两边都先 `git fetch`。**基于 2026-11 改写前历史的旧本机分支一律不推送**：推送前看一下 `git rev-list --count origin/main..HEAD`，数字明显大于这一批的提交数（比如超过 50），就停下来。

## 七、遇到这些情况，停下来

停下来的意思是：不继续改，在 `progress/<批号>.md` 里写清楚情况，PR 状态写「卡住：<原因>」，等用户或协调者处理。

- 计划写的代码事实和实际不符，而且影响到怎么做（只影响数字的，写明差异后可以继续）；
- 带 ★ 的必过项自己检查没过，又不知道怎么修；
- 需要改别人认领的独占文件；
- 需要用户点头的事情（建仓库、删分支、合并、发版、更新截图基线）；
- 发现正式环境（本机已安装的 App、`~/.openclaw`、18789 端口）被改动过，不管是不是自己改的；
- 磁盘剩余空间低于 3GB。

## 八、收工

- 把接力卡的状态改成「待验收」（或「已合并」），「下一步」写成给验收人看的内容，然后推送；
- 删掉自己的临时目录和工作区（`progress` 里引用的证据除外）；
- 确认没有留下占着端口的进程；
- 在 `progress/<批号>.md` 末尾写一段大白话小结：做了什么、哪些过了、哪些没测和原因、下一批要注意什么。
