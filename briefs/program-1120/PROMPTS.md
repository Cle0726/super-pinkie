# 派活和验收的通用提示词

给用户用。把尖括号里的内容换掉，整段复制给 AI 就行。

- `<批号>`：例如 `M2`、`K0`
- `<计划目录>`：M 开头的批写 `briefs/maintenance-1120`，K 开头的批写 `briefs/cle-core-1120`
- `<机器>`：Windows 或 Mac
- `<AI 名称>`：例如 Codex、Claude

计划文件都在 `origin/main` 上。如果 PR #39 还没合并，就在 `origin/docs/maintenance-plan-1120` 上，可以用 `git show <分支>:<文件路径>` 直接读取。

## 一、派活（新开一批）

```text
你是超級碧琪这次整体计划的执行者，负责 <批号> 这一批。只做这一批，做完就停，不要开始别的批次。

仓库：F:\Projects\super-pinkie（Mac 上是对应的仓库路径）。开工前按顺序读完：
1. briefs/program-1120/CONCURRENCY.md：多个 AI 同时干活的规矩，第〇节「接力卡」最重要；
2. briefs/program-1120/README.md 第一节：确认 <批号> 的前置条件已经合进 main，并记下它的独占文件；
3. <计划目录>/PLAN.md：第一、二、三节，以及 <批号> 这一节和「接手规矩」；
4. <计划目录>/ACCEPTANCE.md：通用项和 <批号> 各条；
5. <计划目录>/PROGRESS.md：总表，以及别的批次有没有正在改你要改的文件。

开工步骤：
- 前置条件没满足，或者独占文件被别人认领了，就停下来告诉我，不要开工；
- 按 CONCURRENCY.md 第一、二节：用自己的工作区，从最新的 origin/main 切分支，马上开一个草稿 PR 认领，正文列出要改的文件；
- 新建 <计划目录>/progress/<批号>.md，最上面放接力卡（格式见 CONCURRENCY.md 第〇节）。

干活时：
- 每做完一小步就提交并推送，最长 30 分钟推送一次，同时更新接力卡。任何时候你都可能因为额度用完而停下，下一个 AI 只能靠接力卡接着做；
- 开始超过 5 分钟的操作之前，先在接力卡上写明在跑什么、结果写到哪里；
- 端口和临时目录按 CONCURRENCY.md 3.4 取用。正式环境（本机已安装的 App、~/.openclaw、18789 端口）绝对不碰；
- 遇到 CONCURRENCY.md 第七节列出的情况就停下来，写进接力卡，然后告诉我。

收尾：
- 按 ACCEPTANCE.md 逐条自查，写进 progress/<批号>.md；
- 接力卡状态改成「待验收」，PR 从草稿改为可审阅，然后停止推送；
- 清理临时目录、工作区和后台进程；
- 最后用大白话告诉我：PR 链接、做了什么、哪些过了、哪些没测和原因。

不许做：合并进 main、打 tag、发版、删除分支、更新截图基线、往 known-failures.json 里加条目。这些都要我点头。

网络：本机通过 Clash 代理（127.0.0.1:7897）上网。访问 GitHub 很慢时，只能切换到美国节点。
```

## 二、接手（上一个 AI 做到一半停了）

```text
你接手超級碧琪整体计划里 <批号> 这一批。上一个 AI 做到一半停了（可能是额度用完了），你从它停下的地方接着做。

开工前按顺序读完：
1. briefs/program-1120/CONCURRENCY.md，特别是第〇节第 3 条「接手的 AI 先做这几件事」；
2. <计划目录>/progress/<批号>.md 最上面的接力卡（M0 的在 <计划目录>/PROGRESS.md 里），以及 PR 里的最新留言；
3. <计划目录>/PLAN.md 里 <批号> 这一节和「接手规矩」，以及 <计划目录>/ACCEPTANCE.md 里 <批号> 各条。

然后严格按 CONCURRENCY.md 第〇节第 3 条的五步来：检查有没有没推送的改动、停掉残留的进程、核实最后完成的那一步、在 PR 里留言「接手」，再照着接力卡的「下一步」继续做。

接下来的干活、收尾和「不许做」，都和派活时一样：每一步提交推送并更新接力卡；做完自查，状态改成「待验收」；需要我点头的事情不做。最后用大白话告诉我：接手时的状态、你做了什么、现在的状态。
```

## 三、验收

验收人要和执行者是**不同的 AI 会话**，最好是不同的模型。

```text
你是超級碧琪整体计划 <批号> 这一批的验收人。执行者已经把它标为「待验收」。你只核对，不改代码。

开工前读完：
1. briefs/program-1120/CONCURRENCY.md：第〇节第 4 条（验收人也要写接力卡）和第五节；
2. briefs/program-1120/ACCEPTANCE.md：第一、二节（流程和报告格式）；
3. <计划目录>/ACCEPTANCE.md：开头的「验收人的规矩」「基线」、通用项，以及 <批号> 各条；
4. <计划目录>/PLAN.md 里 <批号> 这一节；
5. 执行者的记录 <计划目录>/progress/<批号>.md（M0 的在 PROGRESS.md 里）。这里写的「过」只当线索，不当结论。

怎么做：
- 用自己的工作区，分离头检出 PR 的最新提交，记下提交号。端口用这一批的端口基数加 5，临时目录按 CONCURRENCY.md 3.4 命名；
- 带 ★ 的条目和通用项（全量门禁、棘轮测试、截图对比、注入对比、正式环境没被碰过）必须亲自重跑；反例类的条目要亲自做反例，做完还原，绝不提交；
- 边核对边写 <计划目录>/review/<批号>.md，最上面放验收人的接力卡，每核对几条就提交推送一次，免得额度用完前功尽弃；
- 写在 Mac（或 Windows）上才能核对的条目，你这台机器做不了的，记为「没测（需 Mac）」，不能记成「过」；
- 除了 review/<批号>.md，不提交任何文件。

结论只能是：通过 / 返工 / 卡住，判定标准见 briefs/program-1120/ACCEPTANCE.md 第一节第 4 条。

最后用大白话告诉我：结论、发现的问题（按严重程度排）、没测的条目和原因、我需要决定的事情。
```

## 四、里程碑检查和总验收

里程碑检查和总验收的内容见 `ACCEPTANCE.md` 第三、四节。要做的时候，把下面这段给一个**没参与过这些批次**的 AI：

```text
你负责超級碧琪整体计划的 <里程碑字母，例如 A，或者「总验收」>。读 briefs/program-1120/README.md、CONCURRENCY.md、ACCEPTANCE.md，以及相关各批的 review/<批号>.md。按 ACCEPTANCE.md 第三节（里程碑）或第四节（总验收）逐项核对，结果写进 briefs/program-1120/milestones/<里程碑>.md 或 FINAL-REVIEW.md，最上面放接力卡，边做边提交推送。你只核对，不改代码。最后用大白话告诉我结论和需要我决定的事情。
```
