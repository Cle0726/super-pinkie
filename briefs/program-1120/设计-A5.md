## 〇、现在有什么、缺什么

下面的接口都在本仓库里核对过（网关部分看的是裁剪 dist `desktop/windows/mac-runtime/openclaw/dist/`，不是完整源码）。

**和「重答 / 换模型」直接有关、已经能用的：**

| 接口 | 位置 | 现在做什么 |
|---|---|---|
| `pinkie.chat.regenerate` | `services/mode-architecture/session-branch.mjs:252-259, 329` | 把叶指针挪到该条用户消息之前，再 `chat.send` 同一段正文和图片。可选参数 `model`（`提供方/模型`，格式 `/^[\w.:@/-]{1,200}$/`）。 |
| `sessions.patch {key, model}` | 同上 `applyModel()`:263-271 | 「只这一次」换模型：先记下原来的模型，patch 成新的，等 `agent.wait` 结束后再 patch 回去（重启也会 `restorePending()`）。 |
| `chat.send` | `session-branch.mjs:226-230` | 真正开一轮。同一会话同一时间只能有一个在跑的轮次。 |
| `pinkie.chat.variants` / `pinkie.chat.switch` | `:182-207, 330-331` | 读同一条用户消息下的多个助手回复，并切到其中一版。 |
| 界面「重新回答」「换个模型重新回答」 | `ui/injections/laolao-message-actions.js:347-348, 193-201` | 前者不带模型（用会话当前模型）；后者弹出「用哪个模型重新回答（只这一次）」，目录来自 `window.__laolaoModelPickerCatalog`，最多列出 40 个。 |
| 失败卡「换成 xx 再发一次」 | 同文件 `:410-422` | 先 `sessions.patch` 再 `regenerate`。这是失败兜底，不是并排。 |
| `sessions.list` 的令牌字段 | dist `sessions-UcKjjh_n.js`（S6 已核对：`totalTokens` / `inputTokens` / `outputTokens`） | 列表里就能看到单个会话的累计用量。 |
| `sessions.usage {key}` | dist `server-methods-NpEcZnvp.js:455`；界面用法 `laolao-metre-perm.js:93-95`（超时 15 秒） | 单个会话的模型、令牌和花费，偏慢。还有 `sessions.usage.timeseries` / `sessions.usage.logs`，并排答第一版不用。 |
| `REVIEW_TOOLS` | `services/mode-architecture/reasoning.mjs:39` | 已有只读工具白名单：`read` / `image` / `pdf` / `web_fetch` / `web_search`。思考档里的审稿员走 `api.runtime.agent.runEmbeddedAgent({ toolsAllow: REVIEW_TOOLS })`（:994-996）。 |
| `sessions.create` + `createBranchedSession` | `session-lineage.mjs:466, 519-532` | 能按某条消息切开一份记录、建一个带指定 `model` 的新会话。 |

**明确没有、或不能拿来做「同一轮两个模型」的：**

1. **同一个会话不能同时跑两轮。** `SessionBranches.busy()` 看到 `hasActiveRun` / `hasActiveSubagentRun` 就拒绝，文案是「这轮跑完再改」（`session-branch.mjs:10, 139-145`）。`variants()` 的注释写明：跑的过程中再拿写锁，等于接管，这一轮的回复不会落盘（:180-181）。所以不能在会话 P 上连续两次 `chat.send` 来并排。
2. **一个会话同一时刻只有一个模型。** 「换模型」是 `sessions.patch` 改掉这个会话的模型，跑完再改回去，不是一次发送带两个模型。
3. **`chat.send` 没有 `toolsAllow` / `disableTools` 参数。** 本仓库里所有限制工具的做法都走 `runEmbeddedAgent`（审稿员、学习伴侣），不走 `chat.send`。裁剪 dist 的 `sessions.patch` 处理函数里也没有 `toolsAllow` 字样；本仓库对 `sessions.patch` 的调用只用到过 `model`、`archived`、`label`、`reasoningLevel`、`unread`。
4. **已有的 `sessions.create({ fork: true })` 不能在父会话还在跑时切开。** 网关会报 `parent session still active`，插件把它转成「父会话还在运行，结束后从提案卡片开启继承上下文的子会话」（`session-lineage.mjs:550-551`）。并排答如果先在父会话上启动一轮，就没法再 fork。
5. **现成的「子会话」通道不是给这个功能用的。** `session-lineage` 的子会话有名额上限、简报、Metre 角色规则，而且「子会话里不能再开子会话」「分身会话不能改」（`session-branch.mjs:132`）。并排答的两个临时会话不要走这条用户可见的子会话树。
6. **`chat.inject` 不能当「把选中的回答写回父会话」用。** #166 的可行性评审已写过：它只写记账消息，下一轮模型看不到。选边之后必须往父会话的 transcript 里写入真正的用户消息和助手消息（或走一次会进入模型上下文的发送路径）。

结论：**第一版需要一个新的插件网关方法**（建议名 `pinkie.chat.sideBySide` 和 `pinkie.chat.sideBySide.adopt`），用两个临时会话并行 `chat.send`，再把选中的那一边写回父会话。不必改内核。不要把这个功能做成「拆分视图里开两个互不相干的会话」，那不是同一题、同一轮。

## 一、用户看到什么

一次并排答是一次「比较轮」，不是两个普通会话。

1. 用户发出（或指定）同一道题。
2. 对话里这道题下面出现左右两栏（窄屏上下叠），每栏顶上是模型名，正文各自流式出现，互不等待。
3. 每一栏能单独停；一边失败或额度用完，另一边继续，失败栏用现有失败卡的口气说明原因，不把整次比较关掉。
4. 两栏都结束（或用户提前选边）后，每栏底部有「用这一边继续」。选中的那一边成为这条用户消息下的正式回复，另一边收成可翻的版本（走已有的「上一版 / 下一版」），比较轮结束。
5. 比较进行中，父会话的输入框不可再发（等同「这轮跑完再改」）；可以停掉整个比较。

820 宽：两栏改成上下叠，先左（模型 A）后右（模型 B），选边按钮仍在各自文末。1440 宽并排。日夜两套都要能看清模型名和选边按钮。

## 二、入口

两个入口，共用同一次比较轮，不要做两套调度。

**A. 发送前（输入框）**

工具托盘「这个会话」分组里加一项「并排答」，和「深度研究」「网页 GPT 协作」同类，不要放进「窗口」分组——那个分组里的「拆分视图」是「两个会话并排放」（`laolao-composer-tray.js:47-51`），不是同一题。

打开后：

- 输入框下方的模型处从「一个模型」变成「两个模型」（见第三节）。
- 发送键文案改成「并排发送」，发出的是一次比较轮，不是普通的一条 `chat.send`。
- 开关只对下一发有效；发出后关掉，避免用户忘了关、以后每句都双倍用量。深度研究那种「下一条生效」的交互可以照着做。

Metre 里同一个开关要是 Metre 的样子，可以再从命令面板加一项「并排答」（现有面板已有「换模型」，`laolao-metre-workspace.js:256`），行为相同。

**B. 发送后（已有回复下方）**

助手消息动作条里，在「重新回答 / 换个模型重新回答」右边加「并排再答」。点开后选两个模型（默认左边是刚才那一答用的模型，右边是上次并排用过的另一个；没有记录就让用户挑）。发起后，以这条用户消息为题再跑一轮比较，原来的回复保留为版本之一。

父会话正在跑、已经有一次比较轮在进行、或这条不在当前分支上：按钮不可用，理由用现有的「这轮跑完再改」。

不在这些地方做入口：拆分视图、新开会话、子会话卡片、系统通知。

## 三、怎么选两个模型

目录和「换个模型重新回答」同一份：`window.__laolaoModelPickerCatalog.present(await catalog.load(agentId))`，`agentId` 从会话键解析，和 `laolao-message-actions.js:194-197` 一样。

规则：

- 必须是两个不同的 `提供方/模型`。选成同一个，提示改用「重新回答」，不要为此开比较轮。
- 每个位子都是完整的模型选择器（提供方 + 模型），不是「左边锁定当前、右边只能选一个」。发送前可以把当前会话模型预填在左边，右边留空直到用户选。
- 第一版不在并排里改思考档位：两套都用该模型当时能用的、和父会话相同的思考档。思考档位本身已经有「同一模型并行多份独立解答」（`reasoning.mjs` 头部说明），和 A5 不是一回事，不要搅在一起。
- 记住每个模式最近一次用过的一对模型，下次打开先填上，可改。
- 某一个模型目录里暂时不可用：那个位子标出来，不让发出去。

## 四、同一轮怎么调度

建议的新方法：

- `pinkie.chat.sideBySide`：开始比较。参数：`key`（父会话）、`models: [左, 右]`、可选 `entryId`（已有用户消息；没有则用这次输入框的正文和附件）。
- `pinkie.chat.sideBySide.adopt`：选边。参数：`key`、`side`（左或右）。
- 再加 `pinkie.chat.sideBySide.abort`：停一边或两边。

内部步骤（都在插件里，不改内核）：

1. 父会话 busy、已有比较轮、模型不合法、两边相同：直接拒绝。
2. 用 `SessionManager` 把父会话当前分支复制到两个临时会话（复制到指定用户消息为止；若是输入框发起，复制现有历史，新题只打到临时会话的 `chat.send` 上）。临时会话用 `sessions.create` 并带上各自的 `model`。键名走内部约定，不要出现在侧栏普通列表里（实现时与 `isInternalSessionKey` / 现有隐藏会话的规则对齐；若必须出现在 `sessions.list` 里，界面要把它们滤掉，不能当用户的子会话展示）。
3. 父会话打上插件自己的「比较中」标记（不要对父会话 `chat.send`），输入框按 busy 处理。
4. 对两个临时会话并行 `chat.send`，同一段 prompt 和附件，各带自己的幂等键。两边各自流式。界面听已有的 `chat` 事件（`delta` / `final` / `error` / `aborted`）和运行事件流，按会话键画到左右栏，不新发明一套流协议。
5. 一边结束或失败不影响另一边。两边都结束时，比较轮进入「待选边」；用户也可以在一边还在流时就选另一边，未选中的那一边 abort。
6. 选边：把「这道用户题 + 选中的助手回复」写入父会话 transcript（成为这条用户消息下的一版，可被 `pinkie.chat.variants` / `switch` 看到），把落选的那一版也作为兄弟版本写进去，然后默认停在选中的那一版。之后归档或删掉两个临时会话。下一句用户消息只在父会话上、只用选中那边的模型（把父会话 `sessions.patch` 成该模型；这是持久选择，不是「只这一次」。若用户只想看、不想改默认模型，选边时另给「继续用原来的模型」——第一版可以先不做，稿里记下，等 win-coord 点头）。
7. 崩溃或重启：比较轮状态要落盘（两个临时会话的键、父会话键、两个模型、发起时的 `entryId`）。起来后若临时会话还在跑，继续画；若只剩结果，进入待选边；若临时会话已经没了，向用户说明这次比较没保住，父会话恢复可输入。

不要用 `runEmbeddedAgent` 当主路径：它是审稿员那种内部 pass，不走会话里那套 `chat` 事件，界面不好复用，失败卡和用量也不在同一条路上。`toolsAllow` 的问题用下面第五节的办法解决，不为此改主路径。

## 五、用量怎么算

原则：**两边都算，选边不退款。** 并排答就是两次完整回答的额度。

展示：

- 每一栏下方写这一边的输入 / 输出令牌；有花费字段就写花费。数据优先用该临时会话在 `sessions.list` 里的 `totalTokens` / `inputTokens` / `outputTokens`（快）；需要模型名或花费时再对这一栏调 `sessions.usage {key}`（慢，15 秒超时，失败就只显示列表里的令牌，不要转圈挡阅读）。
- 比较轮顶部或底部给一行合计：「这一题两边一共 …」。合计是两个临时会话相加，不要把父会话历史累计用量算进来。
- 一边失败时，已产生的令牌仍计入合计，并在该栏标明「未完成」。

记账上这是两个会话的两次 `chat.send`，和现有单次发送没有特殊通道，也不要做「只计选中那边」的隐藏逻辑。若某个模型走的是另一套账号，失败卡沿用 `pinkie.model.failure` 已有的额度 / 恢复时间口气。

## 六、两边的工具调用

**建议：第一版两边都只放行只读工具**，名单就是已有的 `REVIEW_TOOLS`：`read`、`image`、`pdf`、`web_fetch`、`web_search`。不给 `exec`、写文件、编辑、浏览器。理由：

- 两个模型同时动手，会抢同一份工作区，审批也会成双出现，用户难以判断该同意哪一边；
- 并排的目的是比较回答，不是并排改仓库；
- 只读仍能看书、看图、查网页，够大多数「同一题比一比」。

实现约束要写清楚：`chat.send` 本身没有 `toolsAllow`。第一版在插件里为这两个临时会话套一层与审稿员相同的限制——若做不到「对 `chat.send` 注入 `toolsAllow`」而又不许改内核，就只在这两个临时会话上去用已经能限制工具的运行入口，但流式事件仍要转到界面用的 `chat` / 运行事件（这是实现时要打通的一点，见第十一节待核对）。做不到只读限制时，**不要默默放开全部工具**；应在比较轮开始前告诉用户「这一版还不能限制工具，暂不可用」，等 win-coord 决定是补限制还是明确允许两边全工具。

第一版不提供「两边都全放行」的开关。如果以后要开放动手，必须：两边工具串行、写操作都先审批且审批卡片标明是哪一边、默认仍是只读。

## 七、答完怎么选一个继续

- 每一栏结束（`final`）后出现「用这一边继续」。流式过程中也可以点，等于先停另一边再选。
- 必须由用户选。不要按先完成、令牌少、或点赞自动选。
- 选边之后：父会话里这道题下至少有两个版本（选中的和落选的），导航复用已有的「上一版 / 下一版」（`laolao-message-actions.js:320-323`）。当前停在选中的那一版。
- 用户两栏都不想要：提供「都不要，回到比较前」。父会话不加这道新题（若是输入框发起）或保持比较前的那一版（若是并排再答），临时会话归档。
- 选边后输入框恢复。下一句默认跟在选中的那一版后面。
- 比较轮超时（建议 30 分钟，和 `restoreAfter` 里 `agent.wait` 的上限同一量级）：未结束的一边按 abort 处理，已完成的一边仍可被选。

## 八、和现有「换模型重答」的关系

界面上实际文案是「换个模型重新回答」（`laolao-message-actions.js:348`），#96 派活写的是「换模型重答」，指的是同一件事。

| | 重新回答 | 换个模型重新回答 | 并排答（A5） | 拆分视图 | 思考档里的并行独立解答 |
|---|---|---|---|---|---|
| 几个模型同时跑 | 1（当前模型） | 1（另选一个，只这一次） | 2，同时流式 | 两个无关会话，各跑各的 | 同一模型的隐藏 pass，用户不选边 |
| 是否改会话默认模型 | 否 | 否（跑完改回） | 选边后：父会话改成选中那边的模型（见第四节第 6 步，待 win-coord 确认） | 各改各的 | 否 |
| 原回答 | 留作上一版 | 留作上一版 | 并排再答时同样留下；输入框发起则这是新题 | 互不影响 | 不出现在对话里 |
| 适用 | 同一模型再来一次 | 换一个模型再来一次，先看完旧的再开新的 | 还没决定信谁，想对着看 | 两件不同的事 | 提高单次回答质量 |

关系上的硬规则：

- A5 **不取代**「重新回答」和「换个模型重新回答」，三条并排留在动作条上。
- 并排进行中，这三项都不可用。
- 「换个模型重新回答」仍然是「先看完一个，再跑一个」；不要在它的菜单里暗中改成并排。
- 选边产生的版本，必须能被现有的版本切换读到，不要另做一套「比较历史」。

## 九、两种皮怎么呈现

同一份比较轮数据，只换外壳和文案。按 `document.documentElement` 的 `data-laolao-mode` 选皮（与 S6 相同）。

| | 碧琪皮 | Metre 皮 |
|---|---|---|
| 托盘开关 | 「并排答」·「下一句用两个模型同时答」 | 同一开关，口吻改成「下一拍两个模型对着写」 |
| 两栏标题 | 模型名 + 小用量 | 模型名 + 细线用量，和总控台用量块同一画法 |
| 流式 | 现有气泡流式 | 现有 Metre 气泡流式，不要新造一种「声部」 |
| 选边按钮 | 「用这一边继续」 | 「留下这一边」 |
| 都不要 | 「都不要，回到刚才」 | 「都不留，回到刚才」 |
| 区域 | 对话区（登记 `regions.json` 时跟消息动作同一区域） | 同左，Metre 选择器包一层 |

不要把比较轮画进 Metre 总控台或 S6 并行看板里当两个普通在跑会话；若看板能看到临时会话，应折叠在父会话那一行下，标明「并排答」，不能让用户点进去当正式会话用。

## 十一、怎么测

全部在隔离环境，不碰正式 App、`~/.openclaw`、18789。不消耗上游付费额度：模型调用用假网关或本地桩。

1. **Node 单元测试**（纯函数 / 带假 rpc）：两个模型相同被拒绝；父会话 busy 被拒绝；选边后父会话 transcript 里能看到两个版本且当前叶在选中那边；落选和选中都在 `variants` 里；「都不要」不改父会话历史；重启后能恢复「待选边」；一边 `error` 另一边 `final` 仍可选项完成的一边；用量合计是两个临时会话相加，不含父会话历史。
