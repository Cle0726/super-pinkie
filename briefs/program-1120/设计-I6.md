## 〇、现在有什么、缺什么

- **网关没有现成的 `!` 命令**：源码里没有 `commands.bash`，也没有对消息 `startsWith("!")` 的处理；`commands.list` 不是 shell。现在输入 `!ls` 会当普通 `chat.send` 发给模型。
- **能复用的**：
  - 发送拦截点：`ui/injections/laolao-sidebar.js`，在 ws 层拦发送；`:subagent:` 会话已在这里直接回 `INVALID_REQUEST 分身会话只读`。`sessions.steer` 在 :187 直接发出，不进队列；空闲时的 `chat.send` / `sessions.send` 进 `sendQueues`（:192），依次 `ensureProjectScope(key)`（:197，定义在 :423）→ `__pinkieWorkbench.flushContext` → 查 `abortVersions`；`/` 开头的消息在 :204 跳过增强推演。
  - 显示结果：网关 `chat.inject`（源码 `src/gateway/server-methods/chat.ts:5910`，快照 `chat-pg-BxhF6.js:4064`）。参数 `ChatInjectParamsSchema`：必填 `sessionKey`、`message`，可选 `agentId`、`label`（≤100 字），不许多余字段。写成 role=assistant、provider=openclaw、model=gateway-injected，**不调用模型**；而且这类消息是「只留在记录里的记账」，下一轮进模型前会被跳过（`isTranscriptOnlyOpenClawAssistantMessage`）。现有用法 `laolao-web-gpt-collab.js:877`。
  - 放手程度（P2）：审批文件 `exec-approvals.json`（`resolveExecApprovalsPath()`：`OPENCLAW_STATE_DIR` 或 `~/.openclaw`）。合并顺序是文件 `defaults` → `agents[agentId]` → `agents["*"]`，缺省 security `full`、ask `off`。三档见 `ui/injections/laolao-metre-perm.js:47-49`（auto = full/off，ask = allowlist/on-miss，off = deny/off），判档 `levelOf` 在 :51（界面只读 `agents.metre`）。模型 exec 另外还读 `cfg.tools.exec` 的 security / ask（`resolveExecConfig`）。
  - 允许清单（P3）：`ui/injections/laolao-metre-allow.js`，只改 `agents.metre.allowlist`；`window.Pinkie.metreAllow` 只有 `{reload}`，没有可读的「当前清单」，也没有「加一项」的接口。
  - 插件侧：`api.registerGatewayMethod(method, handler, {scope})`（例 `services/mode-architecture/index.mjs:821` 的 `pinkie.model.failure`）；会话在跑 `architecture.activityFor(sessionKey).parentRunning`（背后 `liveParentRuns`，`mode-architecture-core.mjs:45` / `:209`，`index.mjs:817`）；项目目录 `boundProjectRoot(sessionKey, {stateRoot})`（`project-brief.mjs:207`，未绑定返回 `''`）；状态目录 `pinkieStateRoot()`（`mode-constants.mjs:335`）；停止已有 `pinkie.watchdog.cancel({sessionKey})`（scope `operator.admin`，注册在 `index.mjs:1024`，界面在 sidebar.js:177 发）。
- **缺的**：一个插件里的「跑一条命令」网关方法、一个服务端保存的开关、界面上的识别和确认。

## 一、用户看到什么

1. **默认关**。碧琪设置弹层里多一张卡「聊天里用 ! 直接跑命令」（和 P3 的「允许的命令」卡一样走 `pinkie:settings-ready` 挂载），一个开关，下面一句说明：「打开后，以 ! 开头的消息不发给模型，直接在这个会话绑定的文件夹里跑；结果只显示在对话里，模型看不到。」
   - 关着时 `!ls` 照现在一样当普通消息发出去，行为不变。
   - 模型看不到输出是 `chat.inject` 的原生行为（见第〇节），也正好少一条把命令输出（可能含密钥）送进模型的路。要让模型看到，用户把结果复制进下一条普通消息。第一版不做「发给模型」键（要做得另写一条真正的用户记录，见第七节请 win-coord 定）。
2. **打开后**，输入框内容以半角 `!` 开头、后面紧跟非空白字符时，输入框左边出现小标签「命令」（composer 区域）。
   - 不算命令：`!!` 开头（原样去掉一个 `!` 当普通消息发，用来发真的感叹号开头的话）、`! ` 后面是空格、全角 `！`。
3. **按发送**：
   - 能直接跑（见第二节）→ 对话里立刻出一条「命令」消息：`$ <命令>`，跑完补上输出、「退出码 N · X 秒」。
   - 要先问 → 弹确认框：标题「跑这条命令？」，正文是命令原文 + 文件夹路径，两个键「跑」「算了」，默认焦点在「算了」，Esc 等于「算了」。
     - 第一版**不做**「以后这个程序都直接跑」的勾：`window.Pinkie.metreAllow` 没有加清单项的接口，`laolao-metre-allow.js` 本项不改。用户要放行就去 P3 卡里自己加。
   - 不能跑 → 输入框上方一句提示，命令留在输入框里，不发给模型：
     - 「这个代理设成了不跑命令」（P2 = 不跑命令）；
     - 「先给这个会话绑一个文件夹」（没绑项目文件夹）；
     - 「正在回答，先停下再跑命令」（这一轮还在跑）；
     - 分身会话照旧「分身会话只读」。
4. **在跑时**：停止键照常可用，按了就结束这条命令（连带子进程），消息里写「已停止」。超时（默认 120 秒）同样处理，写「超过 120 秒，已停止」。

不做：交互式命令（`vim`、`top`、要输入密码的 `sudo`）——没有标准输入，会等到超时；`cd` 不跨条保留（每条都是新进程，从绑定文件夹开始）。这两点属于 21（R2 每个会话一个终端），本项不等它、也不替它做。

## 二、走不走审批

结论：**走，和模型调用 exec 用同一套档位和清单**。`!` 是用户自己敲的，但页面上的脚本也能伪造发送；所以不因为「是用户敲的」就放宽，也不另起一套规则。

| 这个代理的档位（合并后，见下） | `!` 命令 |
|---|---|
| security `deny`（P2「不跑命令」） | 拒绝 |
| security `full`，ask `off`（P2「自动」，缺省） | 直接跑 |
| security `allowlist`，ask `on-miss`（P2「问我」） | 在允许清单里 → 直接跑；不在 → 弹确认框 |
| ask `always` 或认不出的组合（P2 显示「自定义」） | 每次弹确认框 |

- **判定在服务端做**，界面只负责弹框：`pinkie.shell.run` 自己读审批、自己匹配清单，不信界面传来的「已放行」。界面确认后带 `confirmed: true` 再调一次；服务端只在「本来就该问」的档位上接受 `confirmed`，`deny` 档带了也拒绝。
- **读审批**：优先用原生的 `resolveExecApprovalsFromFile({file, agentId})` / `loadExecApprovals()`（`src/infra/exec-approvals.ts` 约 842、1132 行），前提是插件能拿到（要核对，见第七节）。拿不到才只读 `resolveExecApprovalsPath()` 指向的文件，自己按 `defaults` → `agents[agentId]` → `agents["*"]` 合并、缺省 full/off——不直接 `JSON.parse` 了事。不走 `exec.approvals.get` 网关方法（要 `operator.admin`，参数必须是 `{}`，插件处理函数里调它也绕）。
- **第二层 `cfg.tools.exec`**：模型 exec 还看配置里的 security / ask。本项两层都读，**取更严的那个**，保证不比模型 exec 宽。
- **不走原生审批弹窗**：`exec.approval.request` 存在（`src/gateway/server-methods/exec-approval.ts:147`，scope `operator.approvals`），但参数是一整份运行计划（`command`、`commandArgv`、`cwd`、`host`、`security`、`ask`、`sessionKey`、`timeoutMs`、`twoPhase` …），进程内入口是执行工具专用的 `registerExecApprovalRequest`；插件的 `registerGatewayMethod` 只能注册方法，处理函数里不能直接发这条审批。所以用碧琪自己的确认框。
- **清单匹配**：原生是 `matchAllowlist(entries, resolution, argv?, platform?)`（`src/infra/exec-command-resolution.ts:383`），管道里任一段没被满足整组就不满足（`evaluateAuthorizationPlanGroup`，`exec-approvals-allowlist.ts:784`）；一段满足的来源除了清单还有 safeBins、技能目录、POSIX 安全内建（`:` `cd` `false` `pwd` `test` `true` `[`，Windows 没有）；shell 包装会被拆开看里面的命令。
  - 本项：插件能拿到原生的解析和匹配就直接用（要核对，见第七节）。
  - 拿不到就写一个更窄的纯函数：按 `|` `&&` `||` `;` 切段，**每一段的可执行文件都要在清单里**，或是 POSIX 上那 7 个安全内建；glob 照 `compileGlobRegex`（不带路径按可执行文件名、带路径按完整路径；`*` 不跨 `/`、`**` 跨层；裸 `*` 且无 argPattern 放行全部）。带 argPattern 的清单项在自己实现里**一律不算命中**（按「不在清单」去问），不去重写 argPattern。safeBins、技能目录、拆 shell 包装都不做——结果是比原生窄（例如 `zsh -c 'ls'` 会被问），不会比原生宽。

## 三、默认关，开关存哪

- 存在碧琪状态目录 `pinkieStateRoot()` 下的 `shell.json`（macOS `~/Library/Application Support/SuperPinkie`，Windows `%LOCALAPPDATA%/SuperPinkie`，可用 `PINKIE_STATE_ROOT` 改），`{"enabled": false}`，文件 0600。不进 `~/.openclaw`、不进项目文件夹。
- 网关方法：`pinkie.shell.config.get`（scope `operator.read`，新选择：只回一个布尔值）、`pinkie.shell.config.set`（scope `operator.admin`）。
- `pinkie.shell.run` 每次都先读开关：关着就回 `INVALID_REQUEST`，不管界面怎么调。
- 只有一个全局开关，不按代理分；按代理收紧靠第二节的档位。

## 四、执行细节和 Windows / macOS 差异

`pinkie.shell.run({sessionKey, command, confirmed?})`，scope `operator.admin`：

1. 会话检查，三项分开查：
   - `metreLock.assertSessionAllowed(sessionKey)`——它只在正式版锁着、且会话是 `agent:metre:` / `agent:roles:` 时抛错（`metre-lock.mjs:388`），其他不管；
   - `:subagent:` 会话、只读角色会话，本模块自己拒绝；
   - `architecture.activityFor(sessionKey).parentRunning` 为真就拒绝（插件自己的信号，不用网关侧 `isEmbeddedAgentRunActive`）。
2. cwd = `boundProjectRoot(sessionKey, {stateRoot: pinkieStateRoot()})`；返回 `''` 就拒绝（空串不当家目录，不退回家目录）。
3. 判档（第二节）。
4. 用 `spawn(file, argv)` 起进程，**命令原文只作为一个参数传给 shell**，不拼进别的字符串：

| | macOS | Windows |
|---|---|---|
| shell | `/bin/zsh -l -c <命令>`（登录 shell，PATH 和终端里一致，Homebrew 能用） | `powershell.exe -NoProfile -NonInteractive -EncodedCommand <base64>`（UTF-16LE 编码，省掉引号转义和临时文件；前面加一句把输出编码设成 UTF-8） |
| 为什么不用另一个 | bash 在新系统上是 3.2，和用户终端不一致 | cmd.exe 的引号和编码坑更多；`irm …` 之类本来就是 PowerShell 写法。注意 `desk.mjs:205` 是 `-ExecutionPolicy Bypass -STA -File <脚本>` 跑脚本文件，本项的 `-EncodedCommand` 是新选择，argv 不和 desk 共用 |
| 停止 / 超时 | `detached: true`，`process.kill(-pid, 'SIGTERM')`，2 秒后 `SIGKILL` 整个进程组 | `taskkill /T /F /PID <pid>`（连子进程） |
| 路径 | `/` | 绑定路径原样传，PowerShell 里 `/` `\` 都认 |

5. 环境变量：继承网关进程的环境，但**去掉名字里带 `KEY` / `TOKEN` / `SECRET` / `PASSWORD` / `CREDENTIAL` 的**（不分大小写），避免 `!env` 把网关的密钥打进对话记录。
6. 输出：stdout / stderr 合并，按到达顺序；对话里最多留 16 KB（超了留开头 4 KB + 结尾 12 KB，中间写「省略 N KB」）；去掉 ANSI 颜色码。
7. 结果用 `chat.inject({sessionKey, agentId?, message, label: "命令"})` 写进对话，只传协议里有的字段：开始时一条 `$ <命令>`，结束时一条完整结果（不做流式更新，避免一条命令写几十条记录）。
8. 停止：`laolao-sidebar.js` 的 `chat.abort` 分支已经先发 `pinkie.watchdog.cancel({sessionKey})`；`!` 命令在跑时界面另发 `pinkie.shell.cancel({sessionKey})`（scope `operator.admin`）。
