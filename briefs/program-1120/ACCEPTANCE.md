# 整体计划 · 总验收

每一批「怎样算过」，以各自计划的 `ACCEPTANCE.md` 为准：

- 维护计划：`briefs/maintenance-1120/ACCEPTANCE.md`（通用项 Z1–Z6，以及 M0–M7 各条）
- 内核接管计划：`briefs/cle-core-1120/ACCEPTANCE.md`（通用项 C1–C6，以及 K0–K7 各条）

本文件补充三件事：每一批的验收流程（第一、二节）、里程碑验收（第三节）、全部做完以后的总验收（第四节）。多个 AI 同时干活时的规矩见 `CONCURRENCY.md`，验收人尤其要读第〇节和第五节。

---

## 一、每一批的验收流程

1. **执行者自查**：把对应 `ACCEPTANCE.md` 的每一条填成「过 / 没过 / 没测（原因）」，写进自己的记录文件，接力卡状态改为「待验收」，停止推送。
2. **用户另开一个 AI 当验收人**，用 `PROMPTS.md` 里的验收提示词。验收人和执行者必须是不同的会话，最好是不同的模型。
3. **验收人亲自核对**：带 ★ 的条目和通用项必须亲自重跑，执行者写的「过」只当线索。结果写进 `review/<批号>.md`。
4. **结论只有三种**：
   - **通过**：所有 ★ 都过；不带 ★ 的最多一条没过，并写明不影响用户的理由；
   - **返工**：列出问题表（严重程度、位置、复现步骤、建议），交回执行者。执行者修完后，验收人按 `CONCURRENCY.md` 5.4 重核；
   - **卡住**：需要用户决定，或者计划本身有问题，写明原因，交给用户。
5. **合并**：通过以后，由用户点头合并（规矩见 `CONCURRENCY.md` 第四节）。合并后，执行者把总表上那一行改成「已合并」。

## 二、验收报告的格式

`briefs/<计划>/review/<批号>.md`：

```markdown
# <批号> 验收报告

## 接力卡（最后更新：<时间>，<验收 AI> @ <机器>）
- 核对的提交：`<提交号>`（PR #<号>）
- 已核对：<条目>
- 下一条：<条目>
- 环境：工作区 <路径>；临时目录 <路径>；端口 <范围>

## 结论：通过 / 返工 / 卡住

## 逐条核对
| 条目 | 结论 | 证据（命令、输出原文片段、文件路径） | 复现命令 |
|---|---|---|---|

## 发现的问题
| 严重程度 | 位置 | 复现步骤 | 建议 |
|---|---|---|---|

## 没测的条目
| 条目 | 原因 | 需要谁、在哪台机器补测 |
|---|---|---|
```

## 三、里程碑验收

里程碑包含的各批都通过以后，由一个**没参与过这些批次**的 AI 再做一次里程碑检查，结果写进 `briefs/program-1120/milestones/<里程碑>.md`。这一步比单批验收轻：重点看各批之间有没有互相影响，不重复逐条核对。

| 里程碑 | 必须看到的证据 |
|---|---|
| **A 护栏就位**（M0、M5） | 在最新的 main 上：棘轮测试和截图测试都在 CI 里，并且是绿的；截图测试连续跑 3 次结果相同；故意改坏一个注入文件的样式（只在本地），截图测试会失败。 |
| **B 家底干净**（M1） | 远端没合并的分支只剩「别人正在用」的那类，并且都有负责人；学习台游戏 v4 在 main 上能玩（有截图）；C 类分支都有存档标签；本机的旧工作区已经清理，或者逐个写明保留原因。 |
| **C 维护完成**（M2、M3、M4、M7） | 前后对比表：`!important`、观察器、定时器、全局名、手写版本号、超过 1500 行的文件、真开页面的测试数、截图画面数，基线数字和现在数字各一列；手写版本号为 0；两个巨无霸文件都在 1500 行以内；按 `docs/ARCHITECTURE.md` 随机挑 5 个路径，都存在。 |
| **D 内核等价**（K0、K1、K2） | 碧琪的 Windows 包和 Mac 包里的内核都来自 `cle-core`；全量门禁、截图、注入对比三项都和换内核之前一样；`cle-core` 的第一个提交和上游 tag 逐文件一致。 |
| **E 补丁清零**（K3） | 碧琪仓库里没有任何改上游成品的补丁；`desktop/windows/mac-runtime/` 已删除；`PATCH-MAP.md` 每一行都有去向；每个搬进源码的补丁都有测试。 |
| **F 正式切换**（K4、K5） | 发布出去的版本里，关于页显示「C.le. 内核」；升级和回退在 Mac、Windows 上都实测过，数据都在；测试版用了至少 3 天的记录；用户点头发版的原话。 |
| **G 插件兼容**（K7） | 5 个社区技能、3 个 MCP 服务能装能用；兼容层要么按评估结果做好并通过测试，要么有用户决定不做的记录；社区插件不会自动安装。 |

## 四、总验收（全部做完以后）

在里程碑 A–G 都通过以后进行。由一个新的 AI 会话来做，最好是这次整体计划里**没当过执行者**的模型。结果写进 `briefs/program-1120/FINAL-REVIEW.md`。

1. **从干净的地方开始**：新建工作区，检出最新的 `origin/main`，记下提交号。
2. **全部重跑一遍**：碧琪全量门禁、棘轮测试、截图测试（CI 上的 Linux Chromium，加上 Windows 上的 Edge）、注入对比；`cle-core` 自己的 CI。
3. **对照用户最初要的**（两份 `PLAN.md` 第一节的目标表）：
   - 维护计划 G1–G6、接管计划 H1–H7，每一条写「做到了 / 部分做到 / 没做到」，并附证据。
   - **重点：H3「界面不能变」**。拿 M5 采集的最初截图基线（不是后来更新过的）和现在的截图比对，差异只能出现在 K4 改过的文字区域。
4. **翻查所有验收报告**：每一批的 `review/<批号>.md` 都存在，结论是「通过」；所有「没测」的条目，要么后来补测过，要么写明了为什么可以接受。
5. **检查有没有遗留**：远端没有挂着的 `maint/`、`core/` 分支；没有还开着的认领 PR；本机没有残留的临时工作区；正式环境（已安装的 App、`~/.openclaw`）没有被这次计划的任何一步改过（翻查各批的 Z2 / C4 记录）。
6. **新人测验**：开一个从没接触过这个项目的 AI 会话，只给它 `CLAUDE.md` 和 `docs/ARCHITECTURE.md`，问五个问题：改侧栏背景色改哪个文件；新加一个注入文件要做哪几步；修一个内核的问题要在哪个仓库改、改完怎么让碧琪用上；怎么装一个社区技能；多个 AI 同时干活时，怎么知道别人在做什么。五个都答对才算过，把问答原文贴进报告。
7. **复发记录**：总验收之后一个月内，两份 `PROGRESS.md` 的「复发记录」里，同一个问题如果又出现了，就记下来，作为下一轮改进的起点。
8. **给用户的一页总结**：用大白话写，放在 `FINAL-REVIEW.md` 最前面：做了什么、现在和以前相比好在哪（用前后对比的数字）、还剩什么没做、以后要注意什么。
