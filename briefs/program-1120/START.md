# 碧琪整体计划 · 接活入口

**用户把这个文件发给你，就是请你来接活。** 用户不会另外告诉你做哪一批，也不会再发别的提示词。你自己看清现状，挑一件没人在做的事，做完再挑下一件。照下面的步骤做。

这次的整体计划包括两份：维护计划（`briefs/maintenance-1120/`，批次 M0–M7）和 C.le. 内核接管计划（`briefs/cle-core-1120/`，批次 K0–K7）。同一时间可能有好几个 AI（Codex、Claude 等，在 Windows 或 Mac 上）在做不同的批次。

---

## 第 1 步：找到仓库，读最新的规矩

1. 仓库：Windows 上是 `F:\Projects\super-pinkie`；Mac 上是本机的 super-pinkie 仓库（`git remote -v` 指向 `github.com/Cle0726/super-pinkie`）。
2. 运行 `git -C <仓库> fetch origin`。**不要在这个文件夹里切换分支、也不要改里面的文件**，别的 AI 可能正在用它。读文件一律用 `git show <分支>:<路径>`。
3. 计划文件在 `origin/main` 上。如果 `origin/main` 上还没有 `briefs/program-1120/`，就到 `origin/docs/maintenance-plan-1120` 上读。
4. 你手上这份 START.md 可能是旧的。先读远端的 `briefs/program-1120/START.md`，内容不一样，就以远端的为准。
5. 读完这两份：
   - `briefs/program-1120/CONCURRENCY.md`：全部规矩。**第〇节（接力卡）和第九节（自己挑活）最重要。**
   - `briefs/program-1120/README.md`：第一节的批次表（前置条件、可以同时做的、独占文件、机器）。

## 第 2 步：起名字，看现状，挑一件事

按 `CONCURRENCY.md` 第九节来：

- **起名字**（9.1）：`<模型>-<机器>-<4 位随机>`，例如 `Codex-Win-7f3a`。
- **看现状**（9.2）：开着的 PR、各批的接力卡、两份 `PROGRESS.md` 的总表。
- **按顺序挑**（9.3）：验收 → 接手 → 返工 → 补测 → 里程碑检查或总验收 → 新开一批 → 都没有就向用户汇报。
- **认领，撞车时按规矩让**（9.5）。

挑好以后，在聊天里先用一句话告诉用户：「我是 <名字>，接了 <批号> 的 <执行 / 接手 / 返工 / 验收 / 补测 / 里程碑检查>」，然后按第 3 步对应的那一小节去做。

## 第 3 步：按挑到的事情去做

不管做哪种，都要遵守 `CONCURRENCY.md` 第〇节：**每做完一小步就提交推送并更新接力卡，最长 30 分钟推送一次**；开始超过 5 分钟的操作前，先在接力卡上写明。你随时可能因为额度用完而停下，下一个 AI 只能靠接力卡接着做。

### 3.1 新开一批（执行者）

1. 读那一批的计划：`<计划目录>/PLAN.md` 第一、二、三节，以及这一批那一节和「接手规矩」；`<计划目录>/ACCEPTANCE.md` 的通用项和这一批各条。M 开头的批，计划目录是 `briefs/maintenance-1120`；K 开头的是 `briefs/cle-core-1120`。
2. 建自己的工作区和分支（CONCURRENCY 第一节）：`git -C <仓库> worktree add <盘>:\Projects\pinkie-wt\<批号>-exec -b <maint|core>/<批号小写>-<简短英文> origin/main`。如果计划文件还不在 `origin/main` 上，就从 `origin/docs/maintenance-plan-1120` 切出。
3. 推送第一个提交，马上开**草稿 PR** 认领：标题 `maint(<批号>): <一句话>` 或 `core(<批号>): <一句话>`；正文写「认领：<名字>，<机器>，<日期>」，下面列出要改的文件。然后按 9.5 检查有没有撞车。
4. 新建 `<计划目录>/progress/<批号>.md`，最上面放接力卡（格式见 CONCURRENCY 第〇节）。
5. 照计划做。端口和临时目录按 CONCURRENCY 3.4 取用。遇到第七节列出的情况就停下来，写进接力卡，然后告诉用户。
6. 收尾：按 ACCEPTANCE 逐条自查，写进记录文件；接力卡状态改为「待验收」，「下一步」写给验收人看；PR 从草稿改为可审阅；**之后停止往这个分支推送**；清理临时目录、工作区和后台进程。

### 3.2 接手，或者返工

1. 在那个 PR 下留言「接手：<名字>」（返工就写「返工接手：<名字>」），按 9.5 确认没有撞车。
2. 严格按 CONCURRENCY 〇.3 的五步：读接力卡和留言 → 检查有没有没推送的改动 → 停掉残留的进程 → 核实最后完成的那一步 → 在接力卡上改成自己的名字。
3. 返工的话，先读 `<计划目录>/review/<批号>.md` 的问题表，逐条修改，并在接力卡上写明修了哪几条。
4. 之后和 3.1 的第 5、6 步一样。

### 3.3 验收

你不能验收自己做过的批次；最好和执行者不是同一个模型。

1. 在那个 PR 下留言「验收认领：<名字>」，按 9.5 确认没有撞车。
2. 读 `briefs/program-1120/ACCEPTANCE.md` 第一、二节；读 `<计划目录>/ACCEPTANCE.md` 开头的「验收人的规矩」「基线」、通用项和这一批各条；读计划里这一批那一节；读执行者的记录（执行者写的「过」只当线索）。
3. 建自己的工作区，用分离头检出 PR 的最新提交（`git worktree add --detach <盘>:\Projects\pinkie-wt\<批号>-review <提交号>`），记下提交号。端口用这一批的端口基数加 5。
4. 带 ★ 的条目和通用项（全量门禁、棘轮测试、截图对比、注入对比、正式环境没被碰过）必须亲自重跑。反例类的条目要亲自做，做完还原，**绝不提交**。
5. 边核对边写 `<计划目录>/review/<批号>.md`，格式见 `briefs/program-1120/ACCEPTANCE.md` 第二节，最上面放验收人的接力卡。每核对几条就提交推送一次到被验收的分支上。**除了这个文件，不提交任何东西。**
6. 你这台机器做不了的条目，记为「没测（需 Mac）」或「没测（需 Windows）」，不能记成「过」。
7. 结论只有三种：通过 / 返工 / 卡住（标准见 `briefs/program-1120/ACCEPTANCE.md` 第一节第 4 条）。写进 review 文件，并在 PR 留言「验收结论：<结论>」。通过的，告诉用户「#<号> 可以合并，需要你点头」。

### 3.4 补测

1. 在那个 PR 下留言「补测认领：<名字>」。PR 已经合并的，新开一个小分支和小 PR，标题写 `maint(<批号>) 补测` 或 `core(<批号>) 补测`。
2. 只做标着「没测（需 <你这台机器>）」的那几条，结果写进那一批记录文件的「补测」一节。只提交这个记录文件。

### 3.5 里程碑检查或总验收

1. 开草稿 PR 认领，标题 `program(<字母>): 里程碑检查`，总验收写 `program(final): 总验收`。
2. 按 `briefs/program-1120/ACCEPTANCE.md` 第三节（里程碑）或第四节（总验收）逐项核对，结果写进 `briefs/program-1120/milestones/<字母>.md` 或 `FINAL-REVIEW.md`，最上面放接力卡。只核对，不改代码。

## 第 4 步：做完一件，汇报，接着挑

用大白话向用户汇报，然后回到第 2 步挑下一件，直到没有能做的事，或者需要用户决定。汇报的内容：

- 我是谁，做了哪一批的什么；
- 结果：PR 链接、哪些过了、哪些没测和原因；
- **需要你做的事**：哪个 PR 可以合并、哪件事需要你点头。

没有能做的事时，向用户汇报全局：每一批现在是什么状态、各自卡在什么上，以及把所有接力卡里「待用户决定」的事情汇总成一张清单。

## 绝对不要做的事

- 下面这些事，用户没在聊天里对**这一件事**明确点头，就不能做：合并进 main、打 tag、发版、删除分支、建新仓库、更新截图基线、往 `tools/release-gate/known-failures.json` 里加条目。用户点了头，按 CONCURRENCY 9.7 记下原话再做。
- 碰正式环境：本机已安装的 App（Windows 上是 `%LOCALAPPDATA%\Programs\SuperPinkie`）、它的数据目录（`%LOCALAPPDATA%\SuperPinkie`）、`~/.openclaw`，以及 18789 端口上的正式网关。
- 在别人认领的文件夹、分支上干活；改别人认领的独占文件。
- 推送基于 2026-11 改写前历史的旧本机分支（推送前看 `git rev-list --count origin/main..HEAD`，数字明显大于你的提交数，就停下来）。
- 做计划以外的事，或者觉得「顺手」去改计划没要求的地方。
