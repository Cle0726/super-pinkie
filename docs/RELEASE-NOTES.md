# 更新说明怎么写（每次发版必读）

用户在三个地方看到更新内容：Mac / Windows 的更新弹窗（`ui/injections/laolao-update-dialog.js`），
Windows 装好新版后第一次打开的「碧琪换上新版本啦」卡片，以及 GitHub 发布页 / 国内线路 `latest.json`。
这些全部来自 **一个文件**：`desktop/windows/release-notes.md` 最上面那一节。

## 规矩

1. **一律用碧琪的口吻**，说用户感受得到的变化，不写技术术语。
   - 不写：文件名、路径、代码名（`workboard_*`）、反引号、PR、补丁、网关、重构、计划 X、快照……
   - 写：「碧琪回得更快、更省额度了」「点更新后窗口会关一两分钟，装好会自己回来」。
   - 开发者才关心的细节写进 `CHANGELOG.md`，那里不给用户看。
2. **先一段摘要，再列细节。** 摘要是碧琪说的一段话（要以「碧琪……」来说），挑最有感的一两件，最多 90 字。
3. 细节每条一句话、最多 80 字，最多 8 条；同类的合并。
4. 细节多（超过 2 条或加起来超过 90 字）时，界面上默认只显示摘要，后面跟一个碧琪口吻的展开入口
   「**听碧琪一件件说**」，展开后变成「**先说到这儿**」。不要叫「查看详细」「展开」「更多」。
   细节只有一两句短话时直接摆出来，不出现入口。

## 格式

```markdown
## 2.5.48

碧琪给自己来了一次大扫除：收起一大堆用不上的旧东西，回话更快、更省额度，你的记忆和设置一样没动。

- 碧琪每次开口前要读的说明少了两万多字，回得更快，也更省额度。无限模式照旧。
- ……

<!-- pinkie-notes-end -->

## 2.5.43
（往期，只留作记录）
```

- 标题只写版本号，必须和 `VERSION` 一致；新版本加在最上面。
- `<!-- pinkie-notes-end -->` 放在这一节末尾，旧版 App 读到这里就停。

## 发版时会自动检查

```bash
python3 tools/release/release_notes.py check
```

- `release.yml` 的第一步就跑这条；版本号对不上、没有摘要、摘要不是碧琪口吻、太长、带术语，**发版直接失败**。
- `tests/release_notes_test.py` 也跑同一个检查：改了 `VERSION` 却没写这一节，测试就不过。
- 发布页正文和 `latest.json` 只取这一节（`release_notes.py body`），不会再把往期一起贴出去。

## 读法在哪

- `app/release_notes.py`：唯一的解析 / 检查实现。Windows（`app/windows_desktop.py`）和 Mac
  （`installer/macos/stage-git-update.py`）都用它，返回 `summary` + `details`，另附旧格式 `notes` 给旧版界面。
- Mac 在「检查」时就从 `latest.json` 拿到说明，不用等下载完。
- 旧版 App（2.5.48 及更早）读到新格式时，会把摘要当第一条、细节当后面几条显示，内容不丢。
