## 做法
1. 摸清测试现状：读被测模块代码和项目已有的测试文件，确认测试运行命令，先跑一次现有测试，记下基线结果。
2. 列边界情况列表：动手写测试前，针对被测函数或接口列出要测的场景：正常输入、空值或零值、临界极值、重复输入、非法格式或异常分支、以及简报指定的 bug 复现条件。
3. 编写测试：照项目现有测试框架和目录约定新增或补充测试文件，断言要落在具体的返回值、状态变化或错误类型上，不写只调函数不判断结果的假测试。
4. 每条测试先证明会失败：如果是给未修的 bug 写复现测试，直接跑并记下失败输出；如果是给已有功能补测试，临时把被测断言对应条件改错（或喂错预期）确认测试真能变红，验证后立即还原。
5. 完整重跑：确认所有新增测试和原有测试的结果，检查 `git status` / `git diff` 确保产品代码零改动。
## 边界
- 只改测试文件（以及简报明确允许的测试夹具文件）。严禁修改产品业务代码；测试中发现产品代码有 bug 时，保留能暴露该 bug 的失败测试或复现用例，只报不修。
- 简报和这张卡冲突时以简报为准，并在汇报里说一句。
## 交回
- 新测试清单：测试文件路径、每条用例名称及覆盖的边界情况列表。
- 失败到通过的输出：证明测试在错误条件下会失败、在正确条件下能通过的命令和输出原文（每段最多 30 行）。
- 发现的产品代码问题：只报不修，写清文件路径、行号、触发输入和实际输出（未发现就写「无」）。
