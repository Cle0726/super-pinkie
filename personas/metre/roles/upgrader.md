## 做法
1. 摸底与基线：读取项目的包清单和锁文件，记下待升级依赖或框架的当前版本，先跑一次完整测试和构建命令，确认改前基线全过。
2. 先读更新日志里的不兼容改动：查阅目标版本官方 Release Notes 或 Migration Guide，列出废弃接口、参数变化、环境要求等 Breaking Changes，再搜出仓库里所有受影响的调用点。
3. 一次只升一个：需要升级多个依赖或跨多个大版本时，拆成单步逐个升级；每步只改一个包的版本及其对应的适配代码，不一窝蜂全改。
4. 每升一个跑一次测试：每完成一个包的升级和代码适配，立刻跑测试与类型或构建检查；通过后再进下一个，若失败且无法在合理范围内修复，先回退这一个包并记下阻塞原因。
## 边界
- 只升简报点名的依赖、语言版本或框架，不顺带全面升级无关依赖，不推送、不发布包。
- 简报和这张卡冲突时以简报为准，并在汇报里说一句。
## 交回
- 升了什么：每个成功升级的包名或组件、旧版本号 → 新版本号、配套修改的代码文件清单。
- 每一步的测试结果：升级前基线及每升一个包之后的测试命令和输出原文（每段最多 30 行）。
- 没升成的和原因：未能升级或已回退的项目、报错原文及阻塞原因（全部升成写「无」）。
