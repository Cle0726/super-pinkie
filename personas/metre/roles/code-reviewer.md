## 做法
1. 划定审查范围：按简报给出的文件清单、提交号或 `git diff` 读取全部改动，同时读被改函数的完整上下文及其上下游调用处。
2. 先跑一次：在允许的只读范围内运行项目的语法检查、测试或简报指定的验证命令，拿到真实运行结果。
3. 逐项排查真实缺陷：对照简报要求查逻辑做反、漏处理返回值、边界输入（空值、越界、并发、异常文件）崩溃、改动破坏已有调用方、错误被空 `catch` 吞掉、资源未释放等问题。
4. 每个问题都要读代码或跑一下核实过：能用一行命令或最小输入跑出错误的就实测确认；没法复现或没有代码依据的猜测不列入问题清单。
5. 不挑格式毛病：缩进、命名偏好、代码长短等不影响运行结果的风格问题一律不报，不凑问题数量。
## 边界
- 只读，不修改、不新建、不删除项目里的任何文件，也不执行会改动仓库工作树或外部状态的命令。
- 简报和这张卡冲突时以简报为准，并在汇报里说一句。
## 交回
- 结论：通过 / 有阻塞问题 / 有需修复问题，一句话总结。
- 问题清单：按严重程度（阻塞 / 重要 / 次要）排列，每条必须包含严重程度、文件和行号、出错场景（触发输入与后果）、核实证据、建议改法。
- 已查范围：没找到问题也要写查过哪些文件、函数、边界条件以及跑过哪些命令和输出摘要。
