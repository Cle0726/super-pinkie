# 打法：写代码、改程序

要写一个程序、在已有的项目里加功能、改一段代码、补测试、整理代码时，读这份。报错和跑不起来另见 `debugging.md`；各种语言的装、跑、测命令在 `code-stacks.md`；交付前自查和「帮我看看这段代码」在 `code-review.md`。

原则只有一句：**先看清楚现场，小步改，每一步都真的跑过。** 代码写得对不对不靠感觉，靠运行的结果。

## 零、手边的工具（比自己拼命令可靠）

- `code_search`：找代码。搜内容、按名字找文件、看一个文件的大纲。Mac 和 Windows 一样用，自动跳过依赖和构建产物。
- `code_refs`：一个名字在哪定义、被哪些地方用到。改签名、改名、删代码之前先查。
- `code_edit`：改已有的文件。给原文和新内容；空白和缩进差一点也能对上，对不上时会给回文件里最像的那一段和行号，照它重来。改完自动查语法。新建文件时原文传空串。
- `code_check`：真实的类型、语法、编译检查。
- `run_tests`：跑测试。自动认项目的测试命令；这个会话里第一次跑的结果记为基线，之后每次告诉你哪些是这次弄坏的。所以**动手改之前先跑一次**。认不出命令时用 `command` 参数自己给。
- 这些工具只管当前项目目录里的文件；别处的文件用自带的读写工具。

一轮标准的改动是：`run_tests`（基线）→ `code_search` / `code_refs`（找到并看全）→ 读 → `code_edit`（小步）→ `code_check` → `run_tests`（对比）→ 照真实结果汇报。

## 一、先分清是哪种活

| 这次是 | 最要紧的一件事 |
|---|---|
| 从零写一个程序或脚本 | 先跑通最短的一条路，再一点点加 |
| 在已有项目里加功能、改行为 | 先找到项目里同类的写法，照着它写 |
| 修 bug | 先复现，再改（见 `debugging.md`） |
| 写测试、补测试 | 测试要在代码写错时真的失败 |
| 整理、重构 | 行为一点不能变：改之前测试是绿的，改之后还是绿的 |
| 看代码、讲代码 | 先跑一遍或读完整，再下结论；只说有把握的 |

## 二、摸清一个已有的项目（动手之前，通常 3 到 6 次工具调用）

系统给过「项目速览」的，先信它写的命令和目录，不用重查；没给过就自己看：

1. **看顶层有什么。** 列出顶层目录，认出它是什么项目：`package.json`（Node）、`pyproject.toml` / `requirements.txt`（Python）、`Cargo.toml`（Rust）、`go.mod`（Go）、`pom.xml` / `build.gradle`（Java）、只有 `.html` 的是纯网页。
2. **读它自己的规矩。** 项目里的 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、`README` 里讲怎么跑、怎么测、怎么写的部分。项目自己的规矩比这份打法优先。
3. **找到真实的命令。** 怎么装依赖、怎么启动、怎么跑测试、怎么做检查，从包清单的脚本段（`package.json` 的 `scripts`、`Makefile`、`pyproject.toml`）里读出来。**读不到就说没找到，不编一条看起来像的命令。**
4. **看现状。** 有 git 就 `git status` 和 `git log --oneline -5`：有没有别人没提交的改动、最近在改什么。别人没提交的改动不碰、不覆盖。
5. **先跑一遍测试。** 改之前测试是什么样（全过、本来就有几条失败），记下来。不然改完分不清哪条是我弄坏的。

*为什么：* 一半的返工来自「以为项目是那样」。命令编错一次，后面每一步都建在错的地基上。

## 三、找到该改的地方

- **有 `code_search` 工具就用它搜**（搜内容、按名字找文件、看一个文件的大纲；Mac 和 Windows 都能用，自动跳过依赖目录）。没有这个工具时才用命令行的 `grep -rn` / `Select-String`，并记得排除 `node_modules`、`.venv`。
- **大文件先看大纲。** 几百行以上的文件，先用 `code_search` 的 outline 看函数和类各在第几行，再只读要改的那一段，不整份读。
- **从用户看得见的东西搜起。** 界面上的那行字、报错的原文、接口地址、配置项的名字——这些在代码里通常只出现一两处，比猜函数名快得多。
- **顺着调用走两步。** 找到那一处之后，看谁调用它、它又调用谁（搜函数名）。要改的常常不是找到的那一行，而是它上游的那一行。
- **把同类的都找出来。** 同一个写法在项目里往往不止一处（三个页面都有同一个表单、两个接口都拼同一种日期）。只改用户指到的那一处，其他几处照旧错着，是最常见的漏改。搜一下，一起改，或者在交付时说清另外几处在哪。
- **搜不到就换说法。** 换中英文、换大小写、搜词的一部分、搜文件名。搜三次还找不到，先列目录再读入口文件，从入口往下走。

## 四、改之前

1. **把要改的那个函数完整读完**，再读一个调用它的地方。只看中间几行就改，最容易改坏它前后依赖的东西。
2. **找一个项目里已有的同类写法照着写。** 要加一个接口，先看已有的接口怎么写；要加一个测试，先看已有的测试怎么写。命名、报错方式、目录位置、用的库，全部跟它一样。新写的代码要像原来那些代码的作者写的。
3. **库的用法不凭记忆。** 先看装的是哪个版本（见 `debugging.md` 第二节），用法以这个版本的文档或库的源码为准。记忆里的写法可能是旧版本的。
4. **想清楚怎么验证。** 动手前就定下来：改完之后跑哪条命令、看到什么算对。说不出怎么验证的改动，先别改。

## 五、怎么改

- **一次只改一件事，改完就跑。** 加一个函数，跑一下；接上调用，再跑一下。攒五处改动再一起跑，出错时不知道是哪一处。
- **编辑工具的用法：**
  - 改文件之前先读过它（至少读过要改的那一段），照读到的原文去匹配，空格和缩进一个不差。
  - 要替换的那段文字在文件里必须只出现一次；出现多次就多带上下几行让它唯一。
  - 一次调用只改一处。改完读回那一段，确认改成了想要的样子。
  - 匹配失败时，重新读那一段再改，不凭印象重试，也不因为一次失败就把整个文件重写一遍。
  - 别人的大文件不整份重写：整份重写会悄悄丢掉没读到的那部分。新文件或者自己刚写的小文件才整份写。
- **改了一个东西的样子，就把用它的地方都改掉。** 函数多了一个参数、字段改了名字、返回值换了形状——搜它的名字，每个调用的地方都看一遍。
- **不留垃圾。** 调试用的打印、注释掉的旧代码、没用上的变量和导入、试过又放弃的文件，交付前清掉。
- **不做没要求的事。** 不顺手重构、不升级依赖、不改代码格式、不换写法。看到别的问题记下来，交付时提一句。
- **写一段很长的代码时分几次写。** 先写骨架（函数名和注释），再一个函数一个函数填。一次生成几百行，中间断掉就全白写了，也难检查。

## 六、怎么验（验证梯子，能爬多高爬多高）

| 级别 | 做什么 | 说明了什么 |
|---|---|---|
| 1 语法 | 有 `code_check` 工具就用它（传这次改过的文件）；没有就 `node --check 文件`、`python -m py_compile 文件`、JSON 能解析 | 文件没写坏 |
| 2 检查 | 项目自己的检查命令（`npm run lint`、`tsc --noEmit`、`ruff check`） | 类型和明显的错 |
| 3 测试 | 项目的全部测试，加上为这次改动写的测试 | 逻辑对，没弄坏别的 |
| 4 真跑 | 启动程序，把用户会做的那个操作真的做一遍，看输出 | 真的能用 |
| 5 亲眼看 | 界面改动截图打开看；生成的文件打开看内容 | 用户看到的是对的 |

- **只爬到哪一级，就只能说到哪一级。** 只过了语法检查，就说「写好了，还没跑过测试」，不说「完成」。
- **「应该可以」不算验证。** 这四个字出现在脑子里，就是该去跑一下的信号。
- **没有测试的项目也要真跑一次。** 写一个三五行的小脚本调一下新函数，或者用命令行把那个功能走一遍，看到真实输出。
- **测试没过时：** 先读失败的原文，分清是我的改动弄坏的、还是本来就失败的（对照第二节第 5 步记下的）。不为了变绿去改测试、删测试、跳过测试；测试本身确实错了的，说清为什么再改。
- **命令要等它跑完、读完输出。** 看到命令发出去不等于通过；输出很长就看最后的汇总行和第一个失败。

## 七、从零写一个新程序

1. **选最常见、用户电脑上最容易跑的技术。** 给零基础用户用的小工具：能做成一个双击就开的网页就做网页；要读写本机文件、要定时跑的用 Python；用户的项目已经用了什么就沿用什么。交付时一句话说为什么这么选。
2. **目录从第一天就摆好。** 一个项目一个文件夹；代码、测试、数据分开放；带一份十行以内的 `README`（这是什么、怎么启动、数据存在哪）；`git init`，把密钥文件和依赖目录写进 `.gitignore`。
3. **先跑通最短的一条路。** 记账工具就先做到「记一笔、能看到这一笔、刷新还在」，跑通并验证，然后再加分类、统计、导出。每加一样都跑一次。
4. **依赖要少。** 标准库和已经装了的够用就不加新的；要加就选最主流、还在维护的，并把版本写进依赖清单。
5. **有计算和数据处理就写测试。** 至少覆盖：正常的、空的、边界上的（0、负数、超长、重复）、格式不对的。写完故意把代码改错一处，确认测试会失败，再改回来。
6. **替用户把启动做好。** 配一个双击就能启动的文件（Mac `.command`，Windows `.bat`），在一个干净的终端里从头照着 `README` 走一遍，确认真的能启动。
7. **两种电脑都能跑。** 路径用库来拼（`path.join`、`pathlib`），不手写 `/` 或 `\`；读写文件写明 `utf-8`；不依赖只有一种系统才有的命令。

## 八、交付时怎么说

第一句说做成了什么、怎么用。然后按这个顺序，每样一两句：

- **改了什么**：改了哪几个文件、各自改了什么（用用户听得懂的话，不贴大段代码）。
- **怎么验证的**：跑了什么、看到了什么结果（「全部 42 条测试通过，新加了 3 条」「启动后记了一笔，刷新还在」）。爬到验证梯子的哪一级就说到哪一级。
- **没做的和要注意的**：范围外看到的问题、另外几处同类的地方、我替用户做的假设。

有 git 的项目：改动按一件事一个提交，提交说明写「做了什么、为什么」。只提交这次自己改的文件，不用「全部加入」。不推送，除非用户让推。

## 九、最容易犯的错（发出去之前对一遍）

- 没读文件就改，或者只读了几行就改。
- 库的函数名、参数是凭记忆写的，没查这个版本到底有没有。
- 改了函数，没改调用它的地方。
- 同类的问题有三处，只改了一处。
- 命令是猜的（项目里根本没有 `npm test` 这个脚本）。
- 测试没有真的跑，或者跑了没读输出。
- 用 `try/except: pass`、空的 `catch`、默认值把错误盖住，让它「看起来不报错了」。
- 为了让测试通过去改测试，或者把失败的测试跳过。
- 路径写死成自己这台电脑上的样子（`/Users/某某/…`、`C:\Users\某某\…`）。
- 整份重写了一个大文件，丢了原来的一部分内容。
- 留下了调试打印、临时文件、注释掉的旧代码。
- 说了「完成」，其实只是写完了。

## 十、示范：在一个已有的记账项目里加「按月导出」

用户说：「加个按月导出 Excel 的功能。」

1. 列顶层目录：有 `package.json`，读它——`scripts` 里有 `dev`、`test`、`lint`。读 `README` 里「开发」一节。`git status` 干净。跑 `npm test`：38 条全过。
2. 搜「导出」：找到 `src/export/exportAll.js`（已有「导出全部」）和调用它的按钮 `src/pages/Records.jsx`。完整读这两个文件。项目里已经装了 `xlsx` 库，`npm ls xlsx` 看版本。
3. 定下怎么验证：给 `exportByMonth` 写测试（某个月有 3 笔、某个月没有、跨年的 12 月和 1 月）；再启动页面，点按钮，打开导出的文件看内容。
4. 照 `exportAll.js` 的写法加 `exportByMonth.js`，写测试，跑：新测试 3 条通过。
5. 在 `Records.jsx` 里照已有按钮的写法加一个月份选择和按钮，接上。`npm run lint` 通过，`npm test` 41 条全过。
6. `npm run dev` 启动，选 3 月，点导出，读回生成的文件：3 行，金额和页面上一致。截图看按钮的位置和已有按钮对齐。
7. 提交一次：「记录页加按月导出」。
8. 回复：「**按月导出做好了**：记录页右上角多了一个月份选择，选好点『导出本月』就会下载一个 Excel。空的月份会提示『这个月没有记录』。我跑了全部 41 条测试（新加 3 条），也实际导出了 3 月的 3 笔，和页面上对得上（附截图）。」
