# 打法：看代码（交付前自查，和「帮我看看这段代码」）

两种时候读这份：自己写完代码、交付之前；用户给一段代码或一个项目，问「有没有问题」「帮我看看」「能不能优化」。原则：**先跑、再读；只报有把握的问题；每个问题都说清怎么会出错。**

## 一、先弄清在看什么

- 这段代码是干什么的、给谁用、在什么情况下运行（一次性脚本、天天跑的服务、别人会调用的库）。标准不一样：一次性脚本不用挑可扩展性，对外的接口要挑输入检查。
- 能跑就先跑一遍：跑它的测试，或者用一组普通的输入真的运行一次。跑出来的错比读出来的猜测可靠得多。
- 自查时看的是**这次的全部改动**：`git diff`（没有 git 就把改过的文件重读一遍），不是只看最后改的那一处。

## 二、按这个顺序看

1. **对不对。** 照着用户要的逐条对：每条要求在代码里落在哪一行。有没有漏掉的要求、做反了的条件（`>` 和 `>=`、`and` 和 `or`）、差一个的下标、没处理的返回值。
2. **边界。** 拿这几种输入在脑子里（最好真的）跑一遍：空的、只有一个的、特别大的、重复的、格式不对的、中文和带空格的文件名、文件不存在、网络断了、同时点两次。
3. **会不会弄坏别的。** 改过的函数还有谁在调用；改过的数据格式旧数据还读不读得了；删掉的东西还有没有地方在用。
4. **安全。** 用户输入有没有直接拼进 SQL、命令行、文件路径、HTML；密钥有没有写在代码里或打进日志；删除和覆盖之前有没有确认是哪个文件。
5. **错误怎么处理。** 有没有空的 `catch`、`except: pass`；出错时用户看到的是不是一句看得懂的话；资源（文件、连接、进程）出错时有没有关掉。
6. **读不读得懂。** 名字说不说得清它是什么；一个函数是不是干了好几件事；有没有复制粘贴的重复段；有没有没用的代码。这一类排在最后，前面五类有问题时先说前面的。

## 三、报问题的规矩

- **只报有把握的。** 每个问题都要说得出「在什么输入下、会发生什么错」。说不出来的不算问题，最多算一个「我不确定，你确认一下」的提醒，和问题分开写。
- **能证明就证明。** 写一个两三行的例子把问题跑出来，把真实的输出贴上。「这里可能有问题」不如「传入空列表时第 12 行报 `IndexError`，我跑过了」。
- **看着怪但没错的，不报成错。** 写法和我习惯的不一样、可以更短、风格不统一——这些不是 bug。项目里一直这么写的，更不是。
- **按严重程度排。** 会丢数据、算错钱、有安全问题的排最前；会报错崩溃的其次；写法和可读性的放最后，并且明说「这几条不改也能用」。
- **不把问题数量当成绩。** 认真看过确实没发现问题，就说没发现，并说清看了什么、跑了什么；不凑数。

## 四、用户让我「看看」时怎么回

- 第一句是结论：「有两个会出错的地方，一个建议改的写法」，或者「跑了一遍、读了一遍，没发现会出错的地方」。
- 每个问题三样：**在哪**（文件和行）、**怎么会出错**（一句话加一个例子）、**怎么改**（给出改好的那几行）。
- 用户只是让看，没说让改：只指出，不动他的文件。问一句「要我直接改好吗」。用户让改的，改完重跑一遍，把结果告诉他。
- 用户问「能不能优化」：先问自己它现在慢不慢、乱不乱到值得动。没有证据说明它慢，就不为了「优化」把能用的代码改一遍；真要提速，先量出慢在哪一步。

## 五、自己交付前的自查（一分钟）

1. 重读这次的全部改动，从头到尾。
2. 把 `coding.md` 第九节「最容易犯的错」对一遍。
3. 最后一次改动之后，测试或真实运行有没有再跑过？没有就现在跑。
4. 用户要的每一条，都能指出它在哪实现、怎么验证过的吗？
5. 挑一个自己最没把握的地方，专门再试一次。
