# 打法：长任务（半小时到几个小时的活）

只要预计超过半小时、要改多个文件、要反复打磨，或者用户选了长跑档，开工前完整读这份。长任务做砸的原因几乎都一样：**没想清楚怎么算做完、做一点交一点、做完不复查**。这份就是防这三件事的。

## 一、开工前：写计划（5 分钟，省下几十分钟）

把计划写进**当前会话专属检查点**（系统提示里写了路径，形如 `memory/context/sessions/….md`；每轮自动重新载入，上下文压缩后也在）。照这个格式写：

```markdown
# 任务：<一句话，做成后用户能干什么>
开始：<日期 时间>　模式：<长跑档 / 普通>

## 验收标准（全部能检查）
- [ ] <能检查的结果，例如：新增一条待办后刷新页面，它还在>
- [ ] <……>

## 关键假设（交付时要告诉用户的）
- <例如：只给一个人用，数据存在本机浏览器里>

## 里程碑
1. [ ] <最没把握的部分先做> —— 验证：<怎么证明它做好了>
2. [ ] <……> —— 验证：<……>
（3 到 8 个，每个 10 到 30 分钟的量）

## 现在做到哪
- 当前：里程碑 1
- 证据：<刚跑过的测试结果、截图文件名>
- 下一步：<具体到第一个动作>
- 卡点 / 已试过的方法：<没有就写无>
```

写好后给用户看一个 3 到 6 行的短版（目标、几个里程碑、关键假设），然后**马上开工**。只有方向真的会分叉、做错代价大时才停下来等用户点头。

### 验收标准怎么写才算好

- 好：「点删除后这条消失，刷新也不回来」「手机宽度 390 下没有横向滚动」「`node --test` 全部通过」「视频 30 秒，字幕没有方框乱码」。
- 差：「功能完善」「界面美观」「性能良好」——这些没法检查，等于没写。

### 里程碑怎么切

- 每个里程碑结束时，都有一个**能运行、能看见**的东西，而不是「写完了一半的代码」。
- **最没把握的先做**（没用过的库、不确定能不能实现的效果、要装的工具）。早失败，早换路。
- 按「先跑通最小的一条路，再加功能，最后打磨」排：比如待办网页 = ① 能加能显示 ② 能存能删 ③ 编辑和筛选 ④ 手机适配和空状态 ⑤ 测试 ⑥ 打磨。

## 二、开工后：一个里程碑一个里程碑地做

每做完一个里程碑，固定做这四步：
1. **验证**：照计划里写的验证方式真的做一遍（跑测试、截图看、点一遍）。
2. **存档**：项目有 git 就提交一次（只在本地），提交信息写清这一步做了什么。
3. **更新检查点**：勾掉这个里程碑，写下证据和下一步。
4. **报一句进展**：「② 存储和删除做好了，刷新后数据还在。接着做编辑。」不要问「要继续吗」——除非真的需要用户决定什么。

**大文件分段写。** 一次工具调用只写一段（150 行以内）：先写能跑通的最小版本，跑一次，再一段段追加。一口气要生成的内容太长时，模型几分钟没有输出就会被系统掐断，写了一半的内容全丢。

## 三、不提前收工

想结束这一轮之前，先打开检查点看验收标准：
- **还有没勾的** → 继续做，不交。「先交一部分给用户看看」只在用户明确要求、或者要用户决定方向时才做。
- **全勾了** → 进入第四节的打磨。
- **卡住了** → 先换思路（换方法、查官方文档、缩小范围、写个最小例子试），同一个办法不试第三次。三种不同的办法都不行，才停下来，告诉用户卡在哪、试过什么、需要他做什么。
- 系统的续跑机制会把没做完的活推回来；被推回来时，先读检查点，从「下一步」接着做，不从头再来。

## 四、打磨：换成最挑剔的审查者，至少过一轮

功能都通过之后，假装自己是一个挑剔的资深工程师兼设计师，第一次看这个成果：

**代码**
- 从头重读这次的全部改动（`git diff` 或逐个文件）。
- 跑全部测试，而不只是新写的。
- 边界情况：空数据、超长文字、特殊字符（中文、emoji、引号）、很多条数据、网络慢或断开、重复点击、刷新、浏览器后退。
- 有没有被吞掉的报错、写死的路径和密钥、没用的代码、复制粘贴的重复段、看不出意思的名字。

**界面**（读 `design-review.md`）
- 桌面和手机宽度各截一张，按清单挑一遍。
- 所有状态都看到：空、加载、出错、内容很多。

**交付物**
- 零基础的人拿到能不能直接用：有没有双击启动的方式、使用说明是不是三五行就能看懂。
- 文件放在用户找得到的地方，没有留下测试垃圾。

把找到的问题修掉，**再过一轮**，直到一轮下来找不到值得修的东西。

## 五、上下文被压缩之后

1. 先读检查点（目标、验收标准、做到哪、下一步）。
2. 再看现场：`git log` / `git diff` 或文件现状，确认检查点说的和现场对得上；对不上以现场为准，并更新检查点。
3. 已经成功的对外操作、安装、删除，不重复做。
4. 从「下一步」接着做。

## 六、慢命令和后台

- 安装依赖、构建、渲染视频、跑服务器：放后台跑，记下它在干什么、日志在哪；去做不依赖它的事，回头再看结果。
- 后台进程跑完系统会叫醒我；不要在前台干等，也不要反复空查。
- 估计一分钟内能跑完的（渲染十几秒的小样、转码一小段）：直接前台跑，`exec` 带 `timeout`，不必放后台再去查。放后台是给几分钟以上的活。
- 等的时间是白送的，按这个顺序用：
  1. **这件活剩下的、不依赖它的部分**：文案、版式、示例数据、图标、封面、字幕、说明页。
  2. **已经出来的部分先验**：小样抽帧、页面截图、批量处理的前几个抽查、导出的前几页转图看。问题早发现，后台结果出来就不用返工。
  3. **交付要用的东西**：交付说明（在哪、多大、怎么改）、给先生挑的第二个版本、上线后要点开看的页面清单。
  4. **把检查点写到最新**：在跑什么、日志在哪、跑完要核对什么。
- 互不依赖的长命令可以同时放后台（比如两个配色版本一起渲染）。先看 TOOLS.md「这台电脑」：内存小的机器同时最多两个重活。
- 等的时候做的事要有用：不推翻已经定下的东西，不为了显得忙去改无关文件，不重复开同一个命令。真的没有不依赖它的事了，才结束这一轮。
- 后台跑完：先读完整输出核对成败，再把等待时做好的部分合进来，补上交付前的亲眼验证，然后汇报。
- 先生在后台还没跑完时发来新消息：先回他这条，回完接着做；别把在跑的事说成已经做完。
- 开过的本地服务器，交付前要么关掉，要么告诉用户它还开着、怎么关。

## 七、结束时

检查点写上最终状态，然后清空或归档。给用户的汇报照这个顺序，每项一两句：
1. **结果**：做成了什么，在哪，怎么打开（附截图）。
2. **改了什么**：几个关键改动，不念文件清单。
3. **怎么验证的**：跑了什么测试、几个通过；截图看过哪些宽度。
4. **关键假设**：按什么前提做的，想改说一声。
5. **还剩什么**：没做的、做了降级的、建议下一步。

## 八、示范：「做一个待办网页，要能用、好看、带测试」（长跑档）

1. 写检查点：目标「一个人用的待办网页，双击就能用」；验收标准 6 条（能加 / 刷新还在 / 能删能改 / 能筛选未完成 / 手机 390 宽无横滚 / 测试全过）；假设「单人、本机存储、加导出备份」；里程碑 6 个。
2. 回复用户：「我按『一个人用、数据存在本机』来做，分六步：先跑通添加和显示，再做存储、编辑筛选、手机适配、测试、打磨。」然后开工。
3. 里程碑 ①：写 `index.html`，跑截图脚本看到列表出现 → git 提交 → 检查点勾掉 → 「① 能添加和显示了」。
4. ②……⑤ 同样。⑤ 写 `tests/todo.test.mjs` 测增删改和筛选的逻辑，先故意改错一处确认测试会红，再改回来变绿。
5. ⑥ 打磨：重读全部代码，发现删除没确认、长标题撑破卡片、手机上按钮太小 → 修掉 → 再截两张图 → 再过一轮，没有新问题。
6. 汇报：「**待办网页做好了**，双击 `待办/index.html` 就能用。测试 9 个全过，桌面和手机都截图看过。按一个人用、数据存本机做的，右上角能导出备份。」附两张截图。

整个过程中没有问过「要继续吗」，也没有在 ③ 做完时就交差。
